# Участие в разработке

Проект начинается с требований и плана. Работающего установщика и решения .NET пока нет. Перед изменениями прочитайте [README](README.md), [AGENTS.md](AGENTS.md) и [план разработки](docs/DEVELOPMENT_PLAN.md).

## Объём и предложения

Первый выпуск: C# / Avalonia / MVVM, клиент Windows/Linux, новая установка Media + Home Assistant на Synology DSM 7.x / DS725+ по SSH. Настройка медиасервисов входит в объём. Сеть, облачные привязки, ремонт существующей установки и установка на обычный Linux-сервер отложены.

Если предложение меняет эти границы или порядок этапов, сначала опишите задачу: пользовательский результат, зависимые сервисы, необходимые доступы, последствия изменений и критерии готовности. Не добавляйте архитектурные слои или зависимости только ради возможного будущего использования.

## Рабочий процесс

1. Выберите задачу из этапа плана или согласуйте конкретную проблему в issue.
2. Создайте ветку от актуального `main`, например `feature/install-journal` или `docs/setup-flow`.
3. Сделайте изменение, которое можно проверить отдельно; приложите релевантные тесты и документацию.
4. Проверьте diff, отсутствие credentials и обязательные проверки этого этапа.
5. Откройте PR с описанием проблемы, нового поведения, проверки и ограничений.

Названия примеров веток не являются требованием к существующим веткам. Не сливайте PR и не меняйте чужую инфраструктуру в рамках обычной проверки кода.

## Среда разработки

Целевая основа — .NET 10 LTS, Avalonia и CommunityToolkit.Mvvm. После создания решения SDK закрепляется в `global.json`, NuGet-пакеты — точными версиями и lock-файлами. Пользовательские сборки включают runtime; наличие SDK требуется только разработчикам.

Для разработки клиентского приложения Synology и реальная медиатека не должны быть обязательны. Адаптеры проверяются через фикстуры, локальные тестовые API и отдельные временные окружения.

**Пока нет solution/project-файлов, команды `dotnet restore/build/test` для этого репозитория неприменимы.** Вместе с первым каркасом добавьте точные команды для фактически созданного решения, режим демонстрации и описание Linux-зависимостей. Не публикуйте примеры команд с несуществующими путями.

## Правила кода

- Nullable reference types и анализаторы включены; публичные контракты и важные состояния документируются.
- MVVM обязателен. Views описывают представление, ViewModels — состояние и команды, сценарии установки находятся в Application.
- Доменный и прикладной слои не зависят от Avalonia или конкретных transport-клиентов.
- IO асинхронный, с таймаутами и отменой. Не блокируйте UI и не запускайте конкурентные изменения одного ресурса.
- Ошибки имеют код, пользовательское объяснение и очищенную техническую диагностику.
- Журнал, план и профили имеют версии схем; изменения схем учитывают незавершённые сессии.
- Нельзя полагаться на локализованное имя сущности, первый найденный плеер, фиксированный IP или конкретный Linux path без проверки.
- Новые зависимости требуют обоснования, проверки лицензии и совместимости с обеими клиентскими платформами.

## Проверки

| Тип изменения | Что проверять |
| --- | --- |
| Документация | Ссылки и якоря, согласованность требований, фактический статус, diff, отсутствие секретов |
| Domain/Application | Условия, порядок операций, повторный запуск, ошибки и отмена без реальной инфраструктуры |
| API/SSH-адаптер | Контракт закреплённой версии, неверные доступы, host key/TLS, таймаут, потеря ответа, отсутствие утечки credentials |
| MVVM/UI | Валидацию, переходы, доступность команд, прогресс, ожидание ввода, отсутствие зависания UI |
| Установка и восстановление | Конфликты, частичное выполнение, resume, компенсации, сохранение данных и более поздних изменений |
| Релиз | Сборки Windows/Linux, запуск без установленного .NET, графические зависимости Linux и испытание на заявленной DSM |

CI Windows/Linux добавляется с первым кодом. Закреплённый профиль тестируется на фактических версиях приложений. Успех HTTP-проверки контейнера не доказывает импорт файла, управление ТВ или выполнение сценария.

Аппаратные проверки выполняются только на согласованной тестовой установке. В PR укажите, где проверяли: unit, contract, GUI, Docker-стенд или реальная DSM. Если проверка не выполнялась, напишите это прямо и объясните ограничение.

## Данные и секреты

Не прикладывайте `.env`, `secrets.yaml`, `.storage`, ключи SSH, API-ключи, webhook URL, cookies, пароли, клиентские ключи сопряжения и реальные дампы конфигурации приложений. Для воспроизведения используйте искусственные значения или очищенную диагностику.

Support bundle формируется только после фильтрации чувствительных полей. Скриншоты также проверяются. Если для воспроизведения нужен доступ, вводите его локально в инструмент; публичный issue не является местом для передачи credentials.

Установка не может очищать медиатеку, сбрасывать NAS, отключать TLS или расширять сетевой доступ ради прохождения теста. Изменения production требуют задания, явно охватывающего эти действия.

## Документы и PR

README отражает доступные возможности и известные ограничения; план — будущую работу и критерии; CHANGELOG — внесённые изменения. Обновляйте нужный документ, избегая копирования всей истории обсуждения.

Описание PR должно отвечать на четыре вопроса: что мешало пользователю, что теперь происходит, как это проверено, какие ограничения остаются. Для экранов добавьте очищенный снимок или описание проверки на обеих ОС. Для операций установки укажите результат повторного запуска и восстановления после сбоя.

Документы и пользовательские тексты пишутся по-русски; имена типов и идентификаторы — по-английски. Кодировка UTF-8, окончания строк LF; относительные ссылки учитывают регистр Linux.
