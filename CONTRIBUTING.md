# Участие в разработке

Начните с [README](README.md), [текущей готовности и очереди](ROADMAP.md), [маршрута по документации](docs/README.md), [плана](docs/plans/development-plan.md), применимых ADR и [правил для агентов](AGENTS.md). Требования первого выпуска, клиентская матрица и исключения определяются планом; новую функцию не включайте скрыто в согласованный объём.

## Рабочий процесс

1. Выберите Issue из [карты задач](docs/plans/milestones.md), прочитайте критерии/родителя/зависимости и обозначьте проверяемый результат. Текущий приоритет задают [ROADMAP](ROADMAP.md#очередь-после-независимого-аудита), [ADR 0008](docs/adr/0008-audit-development-sequence.md) и [реестр](docs/audit/2026-10-11-follow-up.md).
2. Проверьте изменения владельца и создайте отдельную ветку. Для независимого design/fixture инкремента объясните, какая часть разрешена до полной приёмки этапа.
3. Обновляйте фактический рабочий статус по [правилам Project](docs/github-project.md). При недоступном API оставьте статус, зависимости и родителей в Issue; не заявляйте обновление доски.
4. Представьте PR с Issue, поведением до/после, проверками и ограничениями; ID находки укажите, если работа выполняется по аудиту. Несвязанные задачи приёмки/упаковки/V2 не требуют искусственного A/B ID. Для частичного выполнения — `Refs #N`, для полного — `Closes #N`. Приёмка GUI/DSM не закрывается от успешного CI.
5. После полной приёмки синхронизируйте эпик, зависимые задачи и статус. Не сливайте PR и не выпускайте tag/release без соответствующего задания.

Новые межэтапные задачи включаются в существующие Milestones/эпики. Не создавайте параллельный backlog аудита и не дублируйте критерии уже существующей задачи.

Обычная база PR — `main`. Если необходим зависимый PR, укажите его базу и порядок интеграции. После слияния родителя переведите оставшийся PR на `main`, проверьте diff и CI. Статус GitHub «Merged» сам по себе не доказывает попадание кода в `main`: проверяйте содержимое и историю целевой ветки, прежде чем объявлять зависимость интегрированной.

## Среда и код

Точный SDK — в `global.json`, central package versions/lock-файлы — в репозитории. [Разработка](docs/development.md) содержит команды, self-contained публикацию и зависимости Linux, [инструменты разработчика](docs/engineering/developer-probes.md) — native probe и изолированные пробы. Locked restore обязателен; lock-файлы меняются при намеренном обновлении зависимостей.

Соблюдайте границы Domain/Application/Infrastructure/Desktop и MVVM ([архитектура](docs/engineering/architecture.md), [стиль кода](docs/engineering/code-style.md)). Пишите развёрнутые условия/методы, один оператор на строку; UI тексты — в Desktop. Форматирование, исправления поведения, архитектурные переносы и обновление версий оформляйте отдельными проверяемыми PR. Настройка formatter/Recommended analyzers/Dependabot/coverage ведётся в #98 и пока не объявляется выполненной.

## Проверки

Для изменений кода: locked restore, Release build, релевантные unit/contract/headless проверки и применимая Windows/Linux матрица CI. Для исправления поведения добавьте регрессию, которая демонстрирует исходную ошибку. Не пишите зеркальные unit-тесты для низкорисковой правки документации.

Для мутаций проверяйте ownership/identity/conflicts, timeout и caller cancellation до/после отправки, lost response и resume. Дедлайн чтения и неизвестный результат записи различаются явным типом. Observe предшествует повтору; 4xx не разрешает повтор без доказательства отсутствия изменения.

Для изменения профиля проверяйте schema/hash/source, pins ↔ clients/probes/CI, параметры ролей и semantic YAML. Свежие секреты и реальные identities пользователя в fixtures не включаются. При рефакторинге HA сохраняйте безопасные auth/session revoke, contract/runtime и flow проверки.

Результат запуска указывает commit/profile/версии, среду, сценарии и ограничения. Fixtures, Docker, CI native GUI, обычный клиентский рабочий стол и настоящая DSM имеют разные доказательства. Незапущенная проверка остаётся непроверенной. Пробы на NAS выполняются только в авторизованном задании и согласованной среде.

## Документация и секреты

[ROADMAP](ROADMAP.md) хранит текущую готовность и очередь; README — назначение/статус/вход, план — требования и зависимости, ADR — причины решений, протоколы — исторические доказательства, CHANGELOG — фактически внесённые изменения. Короткий вход — [docs/README.md](docs/README.md), полный каталог со статусами — [docs/catalog.md](docs/catalog.md); там же [правила размещения](docs/catalog.md#как-поддерживать-документацию). Не копируйте текущие числа тестов в прозу; берите их из отчётов. Исторические числа в датированных доказательствах не заменяйте новыми.

При устранении находки обновите Issue и соответствующую строку реестра аудита с PR/commit и доказательством. Обновление плана не считается исправлением ошибки. Изменение готовности или очереди требует ROADMAP; изменение требований/этапов — плана и ADR.

При добавлении или переносе документа обновляйте каталог и все входящие ссылки в том же PR; текущие контракты держите в действующих описаниях, причины — в ADR, результат конкретной проверки — в датированном протоколе `docs/verification/reports/`. Архив снабжайте исходным срезом и ссылкой на действующее описание. Ссылки, якоря, каталог и типы проверяет DocsCheck (`dotnet run --project tools/HhHomelab.Wizard.DocsCheck --no-build -c Release`, также в CI); UTF-8/LF и diff проверяйте сами. В CHANGELOG один раздел каждого типа внутри версии. UI/документы — по-русски, идентификаторы кода — по-английски.

Credentials/API tokens/OTP/private keys/secret URL не публикуются в коде, логах, снимках, протоколах или PR. Для примеров используйте безопасные синтетические данные. [ADR 0002](docs/adr/0002-journal-and-secrets.md) и AGENTS определяют журнал, unknown outcome, TLS и сохранение данных.
