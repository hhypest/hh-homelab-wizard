# Инструкции для агентов

## Источник требований и состояние проекта

Сначала прочитайте `README.md` и `docs/DEVELOPMENT_PLAN.md`, затем инструкции для затрагиваемого каталога, если они есть. Прямые указания владельца в текущем задании имеют приоритет над этим документом.

M0 начат: есть решение .NET, Domain/Infrastructure, developer tools и unit/fixture-тесты. Application/Desktop, установщика и Avalonia UI пока нет. Прочитайте также `docs/m0/README.md` и протокол проб. Не сообщайте об успешном bootstrap, CI, GUI или испытаниях на NAS без фактического результата. В документах различайте принятые требования, source evidence, fixture-тесты и runtime-проверки.

Закреплённые требования первого выпуска:

- C# / Avalonia / MVVM; интерфейс для Windows 10 x64, Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11; испытания на каждой из трёх ОС обязательны.
- Назначение — новая установка Media + Home Assistant на Synology DSM 7.x / DS725+ по SSH.
- Первичная настройка медиасервисов и связей входит в объём; индексаторы выбирает пользователь.
- Настройка сети, облачных привязок, обычного Linux-сервера, macOS и исправление существующей установки отложены.
- Возобновление установки, начатой этим мастером, входит в объём и не считается режимом исправления.
- Код и машинные профили — MIT; документация — CC BY 4.0.

## Архитектура и MVVM

Владелец выбрал макет **«Фокус»**: [ADR 0005](docs/adr/0005-focus-ui.md). Будущий интерфейс использует центральную колонку, горизонтальные этапы и одно главное действие на экране. На 2026-10-11 разрешена только фиксация выбора; разработка M1 отложена до нового задания владельца. Не трактуйте принятие дизайна как начало реализации.

Целевая структура зафиксирована в плане. Domain/Infrastructure уже созданы; остальные слои добавляются по этапам и не считаются существующими до реализации.

- `Domain` содержит модели плана, операций, проверок и чистые правила. Не зависит от Avalonia, SSH-клиента или HTTP-транспорта.
- `Application` содержит сценарии и интерфейсы внешних сервисов; зависит от `Domain`.
- `Infrastructure` реализует порты: SSH/SFTP, API, хранение журналов, секреты и системные службы.
- `Desktop` содержит Avalonia Views, ViewModels и composition root. Конкретные инфраструктурные сервисы связываются только в composition root.
- MVVM обязателен с первого экрана. Code-behind допускается для жизненного цикла и поведения представления; установка, запросы API и изменения файлов туда не помещаются.
- ViewModels используют абстракции сценариев, сообщают о прогрессе и показывают ошибки. Сервисам нельзя передавать элементы управления, окна или Avalonia Dispatcher.
- Асинхронные команды поддерживают отмену; повторное нажатие не запускает вторую мутацию. Не используйте `.Result` / `.Wait()` в UI.
- Изменения observable-состояния возвращаются в поток UI через предусмотренную границу представления.
- Для новых зависимостей объясняйте необходимость и фиксируйте точные версии. Без preview-пакетов и плавающих версий по умолчанию.

## Планирование и удалённые операции

- Перед изменениями нужен актуальный снимок состояния и конкретный план ресурсов: пути, контейнеры, файлы, настройки и зависимости.
- Проверки окружения выполняются на NAS, где будет работать стек. Доступность сервиса с компьютера пользователя не заменяет проверку из NAS/HA/контейнера.
- В production не исполняйте операции только ради проверки кода. В разработке используйте фикстуры, тестовые API и изолированные окружения.
- Применять к реальному NAS можно в пределах явно авторизованного задания. Не запрашивайте повторное подтверждение, если оно уже дано; не трактуйте запрос на документацию или разработку как разрешение на установку на NAS.
- На уровне продукта запуск конкретного плана пользователем разрешает его обычные операции. Дополнительное решение нужно при обнаружении изменения объёма: чужих данных, занятых ресурсов или необходимости разрушительной операции.
- Не изменяйте DSM firewall, роутер, VPN, DHCP, внешнюю публикацию или облачные привязки ради обхода ошибки установки.
- Не устанавливайте DSM или Container Manager скрыто. Проверяйте prerequisite и выдавайте понятное действие пользователя.
- Не используйте слепое пересоздание интеграций, очистку `.storage`, удаление базы или `docker compose down -v` как исправление ошибки.
- Существующий чужой стек блокирует новую установку. Ресурсы собственной незавершённой сессии допускают возобновление после проверки идентичности.
- Все remote paths проверяются после разрешения абсолютного пути и symlink. Конфигурация и медиатека имеют разные жизненные циклы; медиатека не очищается при откате.
- Не формируйте shell-команды из непроверенных полей UI. Предпочитайте фиксированные операции, передачу параметров через структурированные payload и строгое экранирование POSIX shell при необходимости.
- Учитывайте DSM ACL, `sudo`, права PUID/PGID и доступ к Docker; не делайте рекурсивный `chmod/chown` всей медиатеки.

## Версии и контракты сервисов

- Источник профиля — проверенный tag/commit hh-homelab с закреплёнными версиями образов; не подменяйте его текущим `main` или `latest`.
- API каждого сервиса проверяется на версии профиля. Не переносите предположения об API соседних версий без проверки.
- Для каждого адаптера явно укажите автоматические, интерактивные и пока неподдерживаемые шаги.
- Home Assistant в этом проекте — Container, без Supervisor. Не стройте обязательные операции на API add-on/Supervisor.
- Интеграции и реестры HA изменяйте через их API/config flows. `.storage` допускается включать в резервную копию, но не редактировать вручную для обхода авторизации.
- Pin сторонних компонентов включает версию и проверяемое происхождение. Не запускайте скачанный установочный скрипт без проверки содержимого и версии.
- Изменение внешнего/внутреннего адреса и HTTP-настроек проверяйте по API выбранной версии HA: они не обязаны поддерживать старый YAML-формат.

## Сущности и плееры

- Сопоставляйте DSM по технической метрике, устройству и unique_id; отображаемое имя и язык интерфейса недостаточны.
- Различайте отсутствие сущности, выключение, `unknown`, `unavailable` и ожидание первого измерения. Не превращайте одно в другое для зелёного отчёта.
- Для NAS не смешивайте датчики разных устройств; проверяйте номера/идентификаторы томов и дисков.
- Для LG/GX1/Cast/Jellyfin задавайте конкретные роли; не назначайте случайный первый `media_player`.
- Перед отключением плееров проверяйте ссылки в YAML, UI-конфигурации, панели и динамических шаблонах. Неясная зависимость означает, что автоматическое отключение запрещено.
- Monitor Docker может создавать сущности без редактируемого unique_id. Не обещайте им переименование через реестр.
- Состояние Android TV Remote не является достоверным признаком просмотра. Для Jellyfin/YouTube проверяйте соответствующий источник состояния.
- Не создавайте фиктивные сенсоры и секреты для скрытия отсутствующей интеграции или выключенного модуля.

## Секреты, журналы и восстановление

- Пароли, HA-токены, API-ключи, вебхуки, SSH private keys и клиентские ключи сопряжения не попадают в Git, логи, screenshots, snapshots, PR или support bundle.
- Не передавайте секреты в аргументах процессов. Не выводите полный `docker compose config`, `.env`, `secrets.yaml` или конфигурационные записи с credentials.
- Секреты вводятся локально. Пока безопасное хранилище Windows/Linux не готово, храните их в памяти и запрашивайте заново после перезапуска, а не сохраняйте открытым текстом.
- SSH host key и TLS-сертификаты проверяются. Не вводите автоматическое доверие изменившемуся ключу или глобальное отключение проверки TLS.
- Журнал намерения записывается до отправки изменения, подтверждение — после проверки результата. Запись должна быть атомарной, схема — версионированной.
- При потерянном ответе сначала выясните фактический результат на сервере. Не повторяйте неидемпотентный запрос вслепую.
- Отмена и откат — разные действия. Уже выполненный внешний запрос мог завершиться после отмены локального ожидания.
- У каждой операции описаны компенсация или причина невозможности отката. Не обещайте транзакцию всего NAS.
- Восстановление конфигурации не откатывает накопившуюся медиатеку. Не перезаписывайте более поздние ручные изменения без отдельного решения пользователя.

## Проверки и документы

Команды текущего решения приведены в README и M0 README. Выполняйте locked restore, сборку и релевантные тесты. Для документации проверяйте относительные ссылки, Markdown, фактический статус и diff. Не создавайте фиктивные команды или результаты для отсутствующего UI/установщика.

Обязательны сборка и релевантные unit/contract-проверки на Windows/Linux; UI-проверки добавляются вместе с UI. Для рискованных операций нужны тесты конфликтов, потери связи, отмены, повторного запуска и восстановления; для низкорисковых изменений документации новые unit-тесты не требуются.

Успех на mock-сервере не доказывает работу на DSM. Для аппаратных испытаний сохраняйте версию DSM/HA/профиля, точный сценарий, результат и ограничения без секретов. Не отмечайте незапущенные сценарии успешными.

Обновляйте README при изменении объёма/готовности, план при изменении этапов, CHANGELOG при фактическом изменении поведения. Незавершённые задачи остаются открытыми. Не объявляйте выпуск только из-за добавления документации.

Тексты UI — по-русски, простые и конкретные; технические детали находятся в раскрываемой диагностике. Тексты документации — по-русски; идентификаторы кода — по-английски. Поддерживайте UTF-8 и LF.

## Git и результат задания

- Сначала проверьте состояние дерева и актуальные изменения владельца. Не сбрасывайте и не удаляйте их.
- После начальной инициализации изменения обычно оформляются через отдельную ветку и PR; не сливайте PR без соответствующего задания.
- Не отправляйте сообщения и уведомления внешним пользователям без явного разрешения.
- В результате сообщайте, что изменено, что проверено, какие проверки не запускались и какие решения остаются открытыми.
