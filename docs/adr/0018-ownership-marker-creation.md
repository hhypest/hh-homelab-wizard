# ADR 0018: создание маркера владения как первая журналируемая мутация NAS

- Дата: 2026-10-19.
- Статус: инкремент [#51](https://github.com/hhypest/hh-homelab-wizard/issues/51)/[#53](https://github.com/hhypest/hh-homelab-wizard/issues/53) на fixtures и одноразовом стенде по [ADR 0008](0008-audit-development-sequence.md); реальный NAS не изменяется.
- Основа: [маркер владения](0017-installation-ownership-marker.md), [журнал](0011-local-file-journal.md), [границы операций](0010-operation-boundaries.md).

## Решение

Создание маркера — обычная операция `OwnershipMarker` сервиса `nas` в существующем `ConfigurationOperationScenario`: свежее Observe → атомарный intent в локальном журнале → Apply → независимый Verify → confirm. Второго пути исполнения нет. Ресурс — корень конфигурации на SSH endpoint; спецификация связывает корень, установку и профиль. `OwnershipMarkerRequest` допустим только тогда, когда ресурс, installation ID и профиль совпадают с ожидаемым владельцем.

`NasOwnershipMarkerOperation` реализует и операцию, и `IOperationOwnership`. Каждое Observe, Verify и проверка владения — новый read-only снимок путей с маркером (ADR 0016/0017):

| Наблюдение корня | Состояние | Владение |
| --- | --- | --- |
| Отсутствует, пуст или `staged` без содержимого либо с маркером этой установки | Missing | Owned (новая установка) |
| Точно этот маркер | Satisfied | Owned |
| Чужой маркер, другой профиль, содержимое без маркера, недействительный маркер, корень не прошёл проверку пути | Conflict | Foreign |

Чужое содержимое никогда не принимается: сценарий останавливается до intent.

## Запись

Фиксированный `nas-marker-write.sh`; корень и каноническая однострочная форма маркера передаются через stdin. До первого изменения скрипт проверяет: отсутствие symlink у родителя, корня, каталога и файла маркера и каноничность родителя (`cd -P`/`pwd -P` совпадает с путём — symlink у любого предка отвергается); существование родителя; права чтения, записи и обхода нужного каталога; что корень пуст или содержит только каталог маркера, а тот — только собственные **обычные** временные файлы. Записи перечисляются через glob, а не построчный разбор `ls`, поэтому имя с переводом строки остаётся одной записью. Временный файл получает несуществующее имя и создаётся эксклюзивно (`set -C`), без следования существующей ссылке. Тот же маркер — `already-present` (сравнение побайтно через один и тот же hex-кодировщик и после проверки размера ≤ 4096, без переменных shell, которые теряют переводы строки и NUL), любой другой — отказ. Только после этого создаются корень, каталог маркера и временный файл, затем маркер публикуется `ln` (без замены существующего), временный файл удаляется.

Коды: 0 с точным `marker=created`/`already-present` — подтверждение команды (но не результата: успех даёт только Verify); 2/3 без вывода — доказанный отказ до изменений → `Rejected`. Скрипт ничего не меняет, пока не прочитает запрос целиком, поэтому «отправлено» отмечается только после передачи всего stdin и его закрытия: сбой соединения или передачи раньше — `NotSent` (Transport без изменений); host key соединения записи, не совпавший с pin, — отдельный `IdentityChanged` (Conflict/IdentityMismatch, как при чтении), не транспортная ошибка; всё после отправки, включая таймаут и отмену, — `Unknown`.

Дескриптор привязан к реальной цели: endpoint ресурса обязан совпадать с pin, а профиль ресурса — с профилем каждого свежего снимка; иначе владение не доказано и записи нет.

## Прерывание и продолжение

Обрыв после записи даёт Unknown; новый процесс с тем же журналом видит pending intent, Observe находит этот маркер, независимый Verify подтверждает его — confirm без второй записи.

Если новое Observe при pending intent снова видит Missing (запись не дошла или прервана после `staged`), обычная операция остаётся Unknown без повтора. Операция маркера реализует явный opt-in `IRepeatableConditionalApply`: её Apply — условная запись без перезаписи, которая заново проверяет предусловия на NAS. Только для таких операций сценарий повторяет Apply под **тем же** intent, затем Verify и confirm; ещё работающая прежняя попытка в худшем случае проигрывает гонку `ln` с тем же содержимым. Любой сбой повтора, включая доказанный отказ (код WriteRejected), остаётся Unknown: отказ второй команды ничего не говорит о прежней отправленной попытке, которая ещё может опубликовать маркер; intent остаётся pending до нового Observe/Verify. qBittorrent/Arr и прочие операции этого признака не имеют.

Прерывание между созданием каталога и публикацией оставляет корень только с каталогом маркера и временными файлами мастера. Наблюдение сообщает его как `staged` вместе с общим содержимым непустых временных файлов. Пустой временный файл ещё не записан и никого не называет. Если содержимое есть, оно разбирается как маркер: остаток завершает только названная им установка с тем же профилем; другая установка получает `ownership.foreign-installation`, частично записанный или различающийся между файлами остаток — `ownership.marker-invalid`. Скрипт записи повторно требует, чтобы каждый непустой временный файл побайтно совпадал с запрошенным маркером. Любой другой файл в этом каталоге — обычное содержимое без маркера, оно блокирует.

## Границы

Нет sudo, chmod/chown, fsync каталога и удалённой блокировки: два компьютера с разными журналами могут одновременно пытаться создать маркер одного корня; `ln` гарантирует, что победит один, а второй получит Conflict при Verify/Observe. Компенсация (удаление маркера) не реализована: маркер не содержит данных и остаётся как свидетельство владения. DSM ACL, права PUID/PGID и поведение утилит DSM не подтверждены. Remote lock, executor/recovery #52 и доставка конфигурации #53 — следующие инкременты; полные #51/#53/M3 не закрываются.
