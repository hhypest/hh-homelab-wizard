# ADR 0004: начало M1 и незакрытые проверки M0

Статус: принято 2026-10-11; первый демонстрационный инкремент M1 реализован по новому заданию владельца, см. [ADR 0006](0006-desktop-demo.md). Этот документ не закрывает M0/M1.

## Причина

В M0 уже есть воспроизводимое ядро, профиль исходного проекта, пробы первичной настройки Media/HA и правила неизвестного результата. Оставшиеся задачи включают аппаратные испытания, полный dashboard, дополнительные Media-политики и общий recovery. Их полная реализация до появления Application/Desktop превратила бы исследование в разработку установщика без интерфейса.

В плане зависимость M1 сформулирована как «решения M0 по архитектуре и версиям». Это условие начала каркаса, а полная приёмка M0 подтверждает путь настройки обязательных сервисов. Эти две проверки имеют разный объём.

## Условия начала M1

| Условие | Фактическое состояние |
| --- | --- |
| Слои и MVVM, независимость логики от UI | Приняты в ADR 0001 и AGENTS.md |
| SDK/runtime и воспроизводимое ядро | .NET SDK 10.0.401 / net10.0, locked restore/build/tests, Windows/Ubuntu CI |
| Проверяемая база установки | hh-homelab v1.3.0, точный commit, 9 services / 19 artifacts / 118 steps |
| Первичные контракты и честные ограничения | Media/HA probes, явные интерактивные шаги, Unknown/конфликты; непроверенные функции перечислены отдельно |
| Секреты и неизвестный результат | ADR 0002: память до protected storage, запрет слепого повтора, будущий journal M3 |
| Демонстрационный сценарий без NAS | Реализован первым инкрементом M1 на искусственном адаптере |

Архитектурные условия начала выполнены. Версии Avalonia/CommunityToolkit.Mvvm/DI закреплены в первом инкременте по ADR 0006; клиентская совместимость и ограничения отдельно перечислены в M1 README. Наличие GUI-сборки не закрывает приёмку клиентских ОС.

## Первый инкремент M1

Визуальное направление выбрано владельцем: [«Фокус», ADR 0005](0005-focus-ui.md). Новое задание разрешило разработку; пункты 1–4 ниже реализованы, пункт 5 остаётся частью клиентской приёмки.

1. Добавить работающие Application и Desktop, composition root, базовую навигацию и MVVM.
2. Реализовать демонстрационный сценарий: валидация → выполнение → ожидание ввода → успех либо ошибка; отдельная отмена и запрет второго одновременного запуска.
3. Через абстракцию сценария передавать состояние в ViewModel; возврат изменений в UI thread выполнять на границе представления. Демонстрационный адаптер не выполняет SSH/API/NAS операции.
4. Закрепить стабильные пакеты, сохранить lock-файлы, добавить сборку и релевантные проверки Windows/Linux, выпустить пробные self-contained артефакты.
5. Проверить запуск и графические зависимости в доступной среде. Невыполненные проверки Windows 11 и Ubuntu / X11 и Wayland остаются обязательными для приёмки M1; CI build не заменяет их.

Это каркас с демонстрацией, а не автоматическая установка NAS. Контракты M0 будут переноситься за порты Application по соответствующим этапам; первый экран не получает инфраструктурные клиенты напрямую.

## Что остаётся в M0

- Подтвердить сопряжение и техническую identity настоящих DSM/LG/GX1/Cast, активацию и первые показания DSM; исследование API и fixtures не заменяют эти испытания.
- Проверить DSM build/architecture, SSH/Docker/Compose, права и ACL на согласованном DS725+.
- Дополнить Media-контракты пользователя/policies Jellyfin, настроек playback/transcoding, Arr и выбранных индексаторов/FlareSolverr.
- Проверить полный dashboard и зависимости лишних плееров. Общий durable journal/apply/recovery реализуется в M3/M5; в M0 остаются его контрактные неизвестные.
- Зафиксировать минимальные сборки клиентских ОС и подтвердить совместимость выбранных GUI-пакетов в M1.

M0 остаётся открытым до выполнения своей приёмки. Начало M1 не разрешает применять незавершённые адаптеры к NAS и не меняет объём первого выпуска. Аппаратные проверки и незавершённые API-контракты могут продолжаться вместе с демонстрационным каркасом; установка реального стека требует последующих M2/M3 и соответствующего задания владельца.
