# ADR 0017: маркер владения установкой на NAS

- Дата: 2026-10-19.
- Статус: первый remote-инкремент [#51](https://github.com/hhypest/hh-homelab-wizard/issues/51), только чтение; design/fixtures и одноразовый стенд по [ADR 0008](0008-audit-development-sequence.md).
- Основа: [локальный журнал](0011-local-file-journal.md), [проверка путей](0016-remote-path-inspection.md), [границы операций](0010-operation-boundaries.md).

## Проблема

Локальный session GUID не доказывает владение ресурсами NAS. Проверка путей блокировала любой непустой корень конфигурации, и продолжить собственную прерванную установку было нечем: имя каталога, совпадающие файлы или успешный вход в API не являются доказательством.

## Маркер

`<корень конфигурации>/.hh-homelab-wizard/installation.json` — UTF-8 JSON ровно из трёх свойств: `schema` (1), `installationId` (GUID установки из локального журнала) и `profileFingerprint` (профиль сборки). Без учётных данных, адресов, имён и путей; не больше 4096 байт. Неизвестные или повторные свойства, другой тип, лишние данные после объекта, неверный UTF-8, пустой GUID или неизвестная схема делают маркер недействительным.

Маркер читается в том же read-only SSH-вызове, что и проверка путей: корень конфигурации передаётся строкой `owner=` того же stdin-запроса (`nas-paths-request:v2`). Так пути и маркер наблюдаются одним SSH-пользователем в одно время и попадают в один `RemotePathSnapshot` и его environment fingerprint. Содержимое передаётся hex-строкой (`od -An -v -tx1`), поэтому никакой байт файла не ломает строковый протокол; повреждённая hex-разметка отвергает весь ответ, а недействительный JSON — это наблюдение `Invalid`.

Symlink на любом участке пути маркера даёт `Redirected` без чтения цели. Файл, который не является обычным, или больше 4096 байт — `Invalid`. Если существующий корень или каталог маркера нельзя обойти, наличие маркера неизвестно — `Unavailable`, а не `Absent`.

## Оценка

`InstallationOwnershipAssessment` сравнивает маркер с ожидаемым `InstallationOwner` (installation ID локального журнала и профиль):

| Наблюдение | Код | Статус |
| --- | --- | --- |
| Корня нет или он пуст, маркера нет | `ownership.new-installation` | Passed |
| Маркер совпадает по установке и профилю | `ownership.own-installation` | Passed |
| Маркер другой установки или ожидаемый владелец не задан | `ownership.foreign-installation` | Blocking |
| Своя установка, другой профиль | `ownership.profile-changed` | Blocking |
| Непустой корень без маркера | `ownership.unmarked-contents` | Blocking |
| Маркер недействителен / через symlink / недоступен | `ownership.marker-invalid` / `-redirected` / `-unavailable` | Blocking |
| Корень нельзя проверить | `ownership.configuration-root-unverified` | Blocking |

Эта проверка заменяет прежние `paths.configuration-root.*` из ADR 0016 (до их слияния в `main`). Смена профиля в рамках собственной установки — миграция, которой в первом выпуске нет, поэтому она блокирует, а не продолжает.

## Границы

Совпавший маркер разрешает считать собственным **каталог конфигурации**, но не каждый ресурс внутри него и не контейнеры: inventory Docker по-прежнему блокирует до отдельной проверки ownership контейнеров. Маркер не подписан: он защищает от случайного присвоения чужого стека, а не от намеренной подмены пользователем NAS.

Этот инкремент только читает. Создание маркера — первая мутация установки: она пойдёт через журнал намерений (intent до записи, confirm после независимого чтения) вместе с удалённой блокировкой в следующем инкременте #51/#53. `IOperationOwnership` для отдельных ресурсов ещё не реализован. DSM ACL, sudo и аппаратная проверка не выполнялись.
