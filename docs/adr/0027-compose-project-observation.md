# ADR 0027: read-only наблюдение сети и контейнера Compose-проекта

- Дата: 2026-11-01.
- Статус: частичный инкремент [#50](https://github.com/hhypest/hh-homelab-wizard/issues/50)/[#51](https://github.com/hhypest/hh-homelab-wizard/issues/51) для вертикали [#101](https://github.com/hhypest/hh-homelab-wizard/issues/101), родители #20/#21; fixtures и одноразовый Docker-стенд по [ADR 0008](0008-audit-development-sequence.md). Только чтение.
- Основа: [проверка имени сети](0026-docker-network-preflight.md), [Compose/.env qBittorrent](0023-qbittorrent-configuration-graph.md), [маркер владения](0017-installation-ownership-marker.md).

## Причина

[ADR 0026](0026-docker-network-preflight.md) блокирует любую существующую сеть с выбранным именем и оставляет «проверку labels/Compose project/точной network identity для resume собственной сети» будущей работой. Сеть и контейнер qBittorrent создаёт сам Compose при будущем `up`: отрисованный файл объявляет сеть без `external`, поэтому отдельное `docker network create` сделало бы её чужой для Compose. До записи нужно уметь отличить ресурсы своего Compose-проекта от чужих, не присваивая их по имени.

## Решение

`ComposeProjectIdentity` — то, чем Compose пометит ресурсы этой установки: имя проекта `hhw-<installation ID>` (как в отрисованном `name:`), ключ сети `media` и её имя, сервис и имя контейнера, каталог проекта под корнем конфигурации. `QbittorrentConfigurationRenderer.ProjectIdentity` выводит его из того же запроса и профиля, что и файлы, поэтому значения не расходятся. Имена проходят allow-list Docker (1–63 ASCII, буквы/цифры/`_.-`, первый символ буква или цифра); имя сети — прежнее правило ADR 0026 без точки; каталог — `MediaPathLayout.IsVolumePath`.

Фиксированный `nas-compose-read.sh` получает запрос `nas-compose-request:v1` только через stdin и до обращения к Docker повторяет все проверки; любое отклонение — код 2 без вывода. Docker вызывается только на `unix:///var/run/docker.sock`, переменные окружения Docker удаляются. Используются только `network ls`, `container ls` и `inspect`.

- Точное совпадение имени — Go-template `eq` поверх фильтра `name=`, который допускает подстроку; несовпадения дают пустую строку и пропускаются.
- Для каждого найденного ID метки читаются по одной с точкой после значения и сравниваются **в shell** с ожидаемыми. Значения меток наружу не выходят: точка не даёт подстановке команды обрезать завершающий перевод строки, поэтому `проект\n` не равен `проект`. Каталог проекта в шаблон не подставляется.
- Сеть своя, если `com.docker.compose.project` и `com.docker.compose.network` совпадают. Контейнер свой, если совпадают проект, сервис, `com.docker.compose.oneoff=False` и `com.docker.compose.project.working_dir`. Любая другая или отсутствующая метка — чужой ресурс.
- Состояние контейнера — одно из значений Docker `created|running|paused|restarting|removing|exited|dead`; другое значение делает ответ недоступным.
- Ответ собирается полностью и печатается только после успеха всех вызовов. Отсутствие CLI, отказ socket/daemon, ошибка `inspect` после удачного `ls`, ID неверной длины или больше 16 совпадений дают только `status=unavailable` без записей — не «ресурсов нет» и не меньший полный ответ.

Ответ `nas-compose:v1`: строки `network=<id>:own|foreign`, затем `container=<64 hex>:own|foreign:<состояние>`, `status=available|unavailable`, `end`. Parser отвергает весь ответ при нарушении рамки, порядка, неизвестной записи, состоянии или владении, лишнем поле, записях при Unavailable, ненулевом коде и дублях.

`ComposeProjectFacts` оценивает совпадения консервативно:

| Совпадения | Состояние |
| --- | --- |
| Docker прочитан, совпадений нет | `Absent` |
| Ровно одна своя сеть, не больше одного своего контейнера, чужих нет | `Owned` (с состоянием контейнера) |
| Любой чужой ресурс с этими именами | `Foreign` |
| Только свои ресурсы, но не один согласованный проект (контейнер без сети, два своих контейнера) | `Ambiguous` |
| Неполное чтение | `Unavailable` |

`NasComposeProjectProbe` (порт `INasComposeProjectProbe`) требует одобренный host key той же конечной точки, открывает новое SSH-соединение, не кэширует успех и возвращает неизменяемый `ComposeProjectSnapshot`, привязанный к identity, ключу, principal и профилю. Отпечаток исключает время, включает владение и состояние, поэтому повтор без изменений даёт тот же отпечаток, а остановка контейнера или смена меток — drift.

## Границы

- Только чтение: ничего не создаётся, не запускается, не останавливается, не удаляется, не скачивается и не присваивается по имени. `Owned` — доказательство меток, не lease и не разрешение `compose up`.
- Метки ставит любой, у кого есть доступ к Docker: имя проекта с ID установки и каталог под собственным маркером защищают от случайного совпадения, не от намеренной подделки. Маркер конфигурации проверяют другие шаги графа.
- Соответствие запущенного контейнера отрисованному файлу (`com.docker.compose.config-hash`), образ, порты, health/readiness и метки самой сети, кроме двух названных, не проверяются.
- План ADR 0021/0026 не изменён: существующая сеть по-прежнему блокирует **новую** установку. Использование `Owned` для resume собственной установки, операция `compose up` с Observe/intent/Apply/Verify и readiness — следующие инкременты.
- Swarm-сеть оценивается по тем же меткам; Swarm/overlay не поддерживаются. DSM, Container Manager и реальный NAS не проверены.
