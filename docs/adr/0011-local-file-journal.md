# ADR 0011: локальный файловый журнал сессии

- Дата: 2026-10-18.
- Статус: первый локальный инкремент [#51](https://github.com/hhypest/hh-homelab-wizard/issues/51), до полной приёмки M3.
- Основа: [ADR 0002](0002-journal-and-secrets.md), [контракты операций](0010-operation-boundaries.md), [порядок разработки](0008-audit-development-sequence.md).

## Хранение и идентичность

`FileOperationJournal` реализует существующий `IOperationJournal` для одного локального каталога установки. `Create` — явная инициализация в уже подготовленном каталоге, `Open` — только существующей сессии. Отсутствующие `journal.json`/`journal.lock`, повреждение и несовместимость не создают пустой журнал. Повторная инициализация не перезаписывает файлы. Незавершённая инициализация требует разбора, автоматического сброса нет.

Схема 1 содержит installation/session GUID, отпечаток профиля, generation, intent/confirm и SHA-256 содержимого. Operation/resource identity, service, endpoint/specification hashes и revisions сохраняются из моделей #99. Credential, URL, названия аккаунтов и значения параметров запроса не записываются. Для этих двух операций secret references пока не нужны; защищённое хранилище и перенос остальных Media/HA intent остаются открытыми.

Чтение ограничено 4 MiB, 1024 операциями и глубиной JSON 32. Неизвестные и повторные свойства JSON отклоняются; проверяются схема, hash, scope, уникальность operation ID, resource identity, Missing baseline и Satisfied confirmation. Hash обнаруживает повреждение, но не является подписью и не защищает от намеренной подмены всей сессии либо возврата старой копии между запусками.

Методы требуют lease именно данного descriptor. Изменение endpoint/profile/resource/specification под прежним operation ID блокируется; pending intent не скрывается новым operation ID того же ресурса. Подтверждённая история сохраняется; новая отдельно спланированная операция допустима после подтверждения предыдущей. Адаптер не получает права самостоятельно выдавать новый ID для повтора неизвестного изменения.

## Запись и блокировка

Изменение сериализуется во временный файл в том же каталоге; затем `FileStream.Flush(true)`, закрытие и замена `journal.json`. Orphan temp никогда не используется для восстановления, даже при отсутствии основного файла. Intent публикуется до возврата из `RecordIntentAsync`, confirm — после независимого Verify в Application. Каждый метод перечитывает снимок; замена содержимого во время lease блокирует запись. Отмена во время начавшейся публикации не удаляет намерение.

Стабильный `journal.lock` открыт с `FileShare.None` на всё время Observe/Apply/Verify/confirm. Блокировка охватывает всю установку, включая разные ресурсы. Второй согласованно работающий процесс получает конфликт; после завершения/принудительной остановки первого handle освобождается ОС. Lock-файл остаётся на месте: его нельзя удалять как «устаревший» или заменять, пока возможен работающий процесс. Асинхронные методы выполняют ограниченную файловую работу вне UI-потока.

Предпосылки: приватный каталог на локальной файловой системе, одинаковый путь для всех экземпляров установки, доверенные права и отсутствие стороннего удаления/подмены файлов. На Unix новые файлы создаются с 0600; Windows ACL каталога должен обеспечить будущий host. Обнаруженные symlink/reparse points в пути и файлах отвергаются. Это проверка известных путей, а не защита от злоумышленника, меняющего каталог между проверкой и открытием. Копии каталога, SMB/NFS и разные компьютеры этой блокировкой не объединяются.

Использованные API: [FileShare.None](https://learn.microsoft.com/en-us/dotnet/api/system.io.fileshare?view=net-10.0) и [FileStream.Flush(Boolean)](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0). Проба проверяет завершение **процесса**. Сбой питания, crash файловой системы/ядра и долговечность directory entry после rename не доказаны: отдельного directory fsync здесь нет. До реальных установочных мутаций нужны проверенная политика crash durability, размещение/ACL и удалённая блокировка.

## Продолжение и границы

Используется тот же `ConfigurationOperationScenario`, без второго executor и fallback в память. Новый процесс с pending intent только наблюдает: Missing → Unknown без Apply, Satisfied → независимый Verify и confirm. Подтверждённая запись проверяется заново и даёт AlreadySatisfied; утрата подтверждённой настройки остаётся конфликтом.

Локальный session GUID не доказывает владение NAS. `IOperationOwnership` по-прежнему требует свежего remote marker/instance/profile evidence. Удалённая блокировка, host/preflight, перенос старых клиентских intent, полный граф/recovery, SSH/Docker вертикаль #101 и UI подключения журнала ещё не реализованы. Desktop demo использует искусственный сценарий. Инкремент зависит от PR #109 и не закрывает #51/M3.
