# GitHub Project и прозрачность разработки

Работа ведётся в публичном [Project «hh-homelab-wizard — Разработка»](https://github.com/users/hhypest/projects/3), связанном с этим репозиторием. GitHub Projects принадлежит аккаунту владельца; ссылка доступна также на вкладке Projects репозитория.

[План разработки](DEVELOPMENT_PLAN.md) определяет объём и критерии. [Milestones](https://github.com/hhypest/hh-homelab-wizard/milestones) объединяют задачи этапов; [карта Issues](ISSUE_ROADMAP.md) связывает эпики и зависимости. Project показывает текущую работу над этими же Issues. Он не заменяет приёмку и не добавляет новые функции в объём выпуска.

## Связь с Milestones и Issues

В представлениях видны нативные поля Title, Status, Milestone, Labels, Assignees и Linked pull requests. Milestone берётся из Issue и обновляется GitHub вместе с его назначением. Отдельное редактируемое поле «Этап» не создаётся: перенос задачи между этапами выполняется в самом Issue.

Project представляет Issues существующих Milestones/эпиков. Для новой задачи проверяйте её наличие на доске; родители и blocked-by хранятся нативно в Issues, когда соответствующий API доступен. Ручная копия графа в отдельном поле Project не ведётся.

Текущая готовность продукта — [STATUS](STATUS.md); рабочие приоритеты — [карта Issues](ISSUE_ROADMAP.md). [ADR 0008](adr/0008-audit-development-sequence.md) отличает независимую разработку от условий полной приёмки: native blocked-by родительских эпиков не запрещает явно разрешённый design/fixture инкремент.

GitHub синхронизирует название, Milestone, метки, исполнителей, связи с PR и состояние самого Issue. Status — отдельное поле Project: оно описывает процесс работы и требует ведения по правилам ниже. Будущая задача с зависимостями может оставаться в «План», пока её выполнение не начато. Статус «Заблокировано» используется для ближайшей или уже начатой работы, остановленной конкретным условием.

## Значение статусов

| Status | Условие |
| --- | --- |
| План | Работа запланирована, но выполнение ещё не началось; зависимости описаны в Issue |
| Готово к работе | Можно начинать обозначенную работу без незакрытых обязательных условий |
| В работе | Исполнитель фактически начал работу; для эпика этап уже начат, но ещё не принят |
| На проверке | Результат представлен в PR или протоколе и ожидает проверки/приёмки |
| Ожидает участия | Сейчас требуется целевая ОС, тестовый NAS, устройство или действие владельца |
| Заблокировано | Ближайшая или начатая работа остановлена указанной незакрытой зависимостью |
| Готово | Все критерии выполнены, доказательства приложены, Issue закрыт |

Ожидание обязательного испытания не превращается в «Готово» после успешного CI. Частичный PR может быть слит, а Issue продолжает оставаться открытым. Перемещение карточки в «Готово» не должно использоваться как способ закрыть Issue без приёмки.

## Встроенные правила GitHub

В Project оставлены включёнными встроенные workflows `Item added to project`, `Item closed` и `Auto-add sub-issues to project`. При добавлении задачи применяется начальный статус, который исполнитель проверяет и уточняет; закрытие Issue переводит его в «Готово». Автодобавление sub-issues не является импортом всех новых Issues репозитория: для новой задачи проверяйте её наличие в Project.

Правила `Auto-close issue`, `Pull request linked to issue` и `Pull request merged` удалены из этого Project. Задача закрывается по критериям Issue; слияние частичного PR само по себе не завершает всю работу. Присоединение PR и переход «На проверке» ведёт исполнитель.

Автоматического пересчёта «Готово к работе», «Заблокировано», готовности эпиков и чек-листов нет. После закрытия зависимости исполнитель пересматривает связанные задачи вручную. Не сохраняйте личный GitHub-токен в репозитории или workflow ради такой автоматизации.

## Обязательное обновление при работе

1. Перед началом выберите дочерний Issue, прочитайте эпик и blocked-by. Для новой согласованной работы создайте Issue с Milestone, типом, областью и проверяемыми критериями; добавьте его в Project и свяжите с родителем, если применимо.
2. Укажите фактического исполнителя и поставьте «В работе». В Issue обозначьте следующий проверяемый результат. Для независимой части задачи отдельно объясните, почему оставшиеся зависимости не препятствуют этой работе.
3. При остановке укажите конкретную причину и требуемое действие в Issue. Выберите «Ожидает участия» или «Заблокировано»; сохраните нативную связь blocked-by для зависимости от другой задачи.
4. При открытии PR свяжите его с Issue и поставьте «На проверке». Используйте `Closes #N`, когда PR завершает все критерии; для частичного результата — `Refs #N` с перечислением остатка. Для результата без PR приложите протокол проверки.
5. После проверки завершённой работы закройте Issue, проверьте «Готово» в Project и обновите чек-лист родительского эпика. Пересмотрите задачи, которые зависели от результата. Если PR закрыт без слияния, верните статус к фактическому состоянию.
6. Эпик закрывайте после полной приёмки дочерних результатов, Milestone — после его критериев. При изменении объёма синхронизируйте план, карту задач, Milestone и Issues.

Обновление доски входит в работу над задачей. Если доступа к Project нет, сообщите об этом в результате работы и оставьте точное состояние в Issue; не утверждайте, что Status обновлён. Отсутствие прав на Projects не отменяет требований к приёмке и зависимости.

## Работа после аудита

Выбирайте ближайший Issue по [очереди после аудита](ISSUE_ROADMAP.md#приоритет-после-независимого-аудита), проверяйте его критерии и доступный объём. Доска отображает фактическую работу, а не копию статуса выпуска.

В интеграции #96 созданы #96–#103 и обновлены критерии существующих Issues. Текущие средства GitHub не предоставляют операции Project/native sub-issues/blocked-by: добавление карточек, родителей и нативных зависимостей не выполнено. Резервные рабочие статусы, родители и условия сохранены в Issues. При доступном API синхронизируйте их с Project; не считайте задачу принятой от движения карточки.

Проценты готовности и число тестов не поддерживаются в полях/прозе вручную. Доказательства отличают fixtures, Docker, CI GUI, клиентский GUI и аппаратную DSM; незапущенные проверки не объявляются успешными.
