# Read-only проверка настоящего NAS

Тип: действующий ручной чек-лист для аппаратных проверок #46/#48/#49; выполнение на конкретном NAS не заявляется.

[Инструменты разработчика](../../engineering/developer-probes.md#nasreadonlycheck-read-only-проверка-nas) · [Уровни доказательств](../../engineering/testing.md#уровни-доказательств) · [Текущая готовность](../../../ROADMAP.md)

Проверка запускает на компьютере владельца те же read-only пробы, что мастер использует перед планом: SSH-подключение, preflight NAS, пути и маркер владения, имя Docker-сети и наблюдение Compose-проекта. **Ничего на NAS не создаётся, не меняется и не удаляется**: нет записи файлов и каталогов, `chmod/chown`, создания сетей, `docker pull/run/compose up`, sudo-команд и изменения настроек DSM. Мутации настоящего NAS выполняются только после готовности M3, по отдельному согласованному плану и явному разрешению владельца.

## Что нужно

- Компьютер в той же локальной сети, что NAS. Windows 11 x64 или Linux x64.
- Включённая служба SSH в DSM и учётная запись, которой мастер будет пользоваться (в DSM вход по SSH разрешён администраторам). Пароль или закрытый ключ этой учётной записи остаются на компьютере: инструмент спрашивает пароль и фразу ключа без отображения и никогда не принимает их аргументами, не пишет в отчёт и консоль.
- Инструмент `NasReadOnlyCheck`: архив `hh-homelab-wizard-nas-read-only-check-win-x64` (или `-linux-x64`) из артефактов CI нужного commit, распакованный целиком; либо запуск из исходников с SDK из `global.json`: `dotnet run --project tools/HhHomelab.Wizard.NasReadOnlyCheck -c Release -- <аргументы>`.
- Выбранные для будущей установки корень данных и корень конфигурации под `/volumeN` и имя Docker-сети. Существующий стек hh-homelab при этом не трогается.

## Шаги

| ID | Действие | Ожидаемый результат |
| --- | --- | --- |
| NR01 | `HhHomelab.Wizard.NasReadOnlyCheck.exe --host <адрес NAS> --user <учётная запись> --password` (или `--key <файл ключа>`) | `ssh: host key approval required`, строка `ssh.host-key: <алгоритм> SHA256:…`, код выхода 3. Подключение не продолжается без одобрения ключа |
| NR02 | Сверить отпечаток ключа сервера независимым путём, например выводом `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` на самом NAS | Отпечатки совпадают. Несовпадение — остановка проверки, ключ не одобряется |
| NR03 | Повторить NR01 с `--host-key "<алгоритм> SHA256:…"`, `--data-root`, `--config-root`, `--network` и `--report nas-read-only.json` | `ssh: Ready` (или `SftpUnavailable`, если SFTP выключен в DSM), затем `preflight: Ready`, `paths: Ready`, `network: Ready`, `compose: Ready`; итог `nothing on the NAS was changed`, код 0 |
| NR04 | Просмотреть строки `preflight.*` | Версии DSM, Container Manager, Docker, Compose, модель, тома и порты прочитаны; отсутствующее — `Missing`/`Unavailable`, а не догадка. Blocking-проверки допустимы и записываются как результат |
| NR05 | Просмотреть строки `paths.*` | Для каждой роли: каталог/отсутствует/недоступен, совпадение канонического пути, владелец и режим; маркер владения `Absent` для нового корня конфигурации |
| NR06 | Просмотреть `network.*` и `compose.*` | Для нового имени сети совпадений нет, `compose.state: Absent`. Если имя совпадает с сетью существующего стека — `matches=1` и `compose.state: Foreign`: чужая сеть не присваивается |
| NR07 | Повторить NR03 через несколько минут | Те же значения; изменения объясняются изменениями на NAS, а не самим чтением |

## Запись результата

Датированный протокол в `docs/verification/reports/` с commit инструмента, версией DSM/модели и итогом NR01–NR07. Отчёт `nas-read-only.json` не содержит паролей, ключей, адреса, имени пользователя и ID контейнеров, но содержит пути, UID/GID и порты: в публичный протокол переносится только сводка. Успешное чтение не означает готовность к установке и не закрывает DSM ACL, сопряжение устройств и мутации.
