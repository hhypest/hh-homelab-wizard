# План разработки hh-homelab-wizard

Дата базовых требований: **10 октября 2026 года**. Этот документ определяет требования и критерии этапов. Текущая готовность хранится в [STATUS](STATUS.md), доказательства — в протоколах [M0](m0/README.md) и [M1](m1/README.md). Порядок работы после аудита уточнён [ADR 0008](adr/0008-audit-development-sequence.md); наличие описания не означает реализации.

## 1. Принятые требования

Исполнение этого плана ведётся через [Project](https://github.com/users/hhypest/projects/3), [Milestones](https://github.com/hhypest/hh-homelab-wizard/milestones) и [карту связанных Issues](ISSUE_ROADMAP.md). План определяет требования и критерии этапов; Issues фиксируют конкретную работу, зависимости и доказательства приёмки. [Правила Project](PROJECT.md) определяют отображение текущей работы и обновление статусов. Состояния задач читаются из GitHub, а не из наличия описания или кода.

| Вопрос | Решение владельца |
| --- | --- |
| Язык и интерфейс | C#, Avalonia, MVVM |
| Клиент | Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland; Windows и оба сеанса Linux обязательны для испытаний |
| Целевая машина | Synology DS725+, DSM 7.x, SSH; первая аппаратная проверка — DSM 7.4.1-90080, версия сообщена владельцем |
| Сценарий | Только новая установка; продолжение собственной прерванной установки обязательно |
| Media | Первичная настройка аккаунтов, папок, qBittorrent, Prowlarr, Radarr/Sonarr, Jellyfin и Seerr; индексаторы выбирает пользователь |
| Home Assistant | Интеграции, сущности, панель и проверка автоматизаций, с учётом Jellyfin и YouTube |
| Исключения | Настройка сети и облачных привязок; исправление существующей установки и обычный Linux-сервер — позже |

Цель первого полноценного выпуска: пользователь устанавливает оба стека через графический мастер и получает проверяемый результат без редактирования YAML и массового ручного переименования сущностей. Подтверждение на экране устройства, ввод PIN, выбор индексаторов и предоставление доступов остаются нормальными интерактивными шагами.

Новая установка сохраняет уже существующую медиатеку. Чужие контейнеры, конфигурации и базы приложений не переиспользуются автоматически. Ресурсы незавершённой сессии самого мастера допускают продолжение после проверки идентичности, профиля и состояния.

## 2. База установки и совместимость

Первый профиль строится по [hh-homelab v1.3.0](https://github.com/hhypest/hh-homelab/tree/v1.3.0), commit `b05047b081f3543520582315002e359ef1d93e59`. Версия мастера независима от версии hh-homelab. Новые изменения upstream не подхватываются посреди установки.

Профиль должен содержать:

- версию схемы, идентификатор, tag/commit источника, перечень файлов и контрольные суммы;
- точные версии образов и сторонних компонентов, происхождение и лицензии;
- ограничения DSM/Docker/Compose, пути, параметры, используемые API и обязательные проверки;
- граф операций, роли сущностей, ожидаемые идентификаторы и зависимости автоматизаций;
- флаги опциональных модулей, требования к действиям пользователя и условия готовности;
- ссылки на секреты без самих значений.

Исходный состав: семь сервисов Media — qBittorrent, Prowlarr, Radarr, Sonarr, FlareSolverr, Jellyfin, Seerr; отдельно Home Assistant Container и Docker Socket Proxy. Monitor Docker устанавливается как компонент HA, а не дополнительный контейнер. Профиль наследует версии из указанного commit; их обновление требует отдельной проверки контрактов.

Начальная клиентская матрица: Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland; целевые сборки — `win-x64` и `linux-x64`. Выбор платформ согласован владельцем; автоматические native-пробы пройдены, интерактивная клиентская приёмка ещё не завершена. Минимальные сборки Windows и совместимость выбранных SDK/пакетов фиксируются в M0/M1. Поддержка всех DSM 7.x не считается доказанной испытанием одной сборки: публикуется проверенная матрица, остальные версии получают статус непроверенных.

Технологическая основа: .NET 10 LTS / SDK 10.0.401, Avalonia 12.1.4 (включая Avalonia.Wayland), CommunityToolkit.Mvvm 8.4.2, DI 10.0.12, [ADR 0006](adr/0006-desktop-demo.md). Пробные сборки включают .NET runtime; пользователю не нужны Python, Node.js или установленный .NET. Для Linux перечислены системные библиотеки, окончательная клиентская приёмка остаётся открытой. По решению владельца Windows 10 исключена из целевых платформ; Linux проверяется отдельно в X11 и нативном Wayland, [ADR 0007](adr/0007-client-platforms.md). Ubuntu 24.04 LTS x64 остаётся базовым дистрибутивом, остальные дистрибутивы требуют отдельного подтверждения совместимости.

## 3. Пользовательский сценарий

| Экран | Действия и результат | Ошибки и альтернативные состояния |
| --- | --- | --- |
| Начало | Выбор профиля, объяснение границ новой установки | Обнаружение собственного журнала предлагает продолжение |
| NAS | Адрес, SSH-доступ, проверка ключа сервера | Изменившийся ключ, отказ доступа, истёкший таймаут |
| Проверка окружения | DSM, Docker/Compose, права, место, порты, пути, конфликтующие ресурсы | Блокирующие ошибки отдельно от предупреждений; повторная проверка после исправления |
| Media | Пользователь и UID/GID, каталоги, категории, качество, библиотеки, индексаторы | Несовместимые пути/права, неполные доступы, разные файловые системы |
| Home Assistant | Доступы, адреса устройств, роли, локальные и опциональные функции | Требуемое устройство отсутствует; опция выключена с явными последствиями |
| План | Конкретные файлы, контейнеры и настройки, ожидаемые изменения | Изменение входных данных пересоздаёт план; устаревшее наблюдение требует проверки |
| Установка | Прогресс по операциям, ожидание PIN/подтверждения, повторная проверка связи | Ошибка, отмена, неопределённый результат запроса, продолжение после перезапуска |
| Проверка результата | Сопоставление сущностей, панель, тесты Media/HA | Не найдено, отключено, unknown, unavailable и ожидание показаний различаются |
| Завершение | Адреса сервисов, отчёт, выполненные и оставшиеся действия | «Завершено с ограничениями» не выдаётся за полную готовность |

Пользовательский интерфейс и документация сначала на русском. Техническая диагностика раскрывается отдельно. На каждом шаге понятны причина остановки и следующее действие. Требуются клавиатурная навигация, видимый фокус, подписи полей, сообщения об ошибке рядом с полем; статус не передаётся только цветом.

Нет общего процента, рассчитанного из предположительной длительности разных операций. Показываются завершённые этапы и фактический прогресс там, где источник его предоставляет. Секреты замаскированы и исключены из отчётов. Ожидание подтверждения устройства сохраняет прогресс и не блокирует интерфейс.

## 4. Архитектура и будущая структура

Созданы Domain, Application, Infrastructure, Desktop, UnitTests и DesktopTests (headless UI). Application содержит искусственный сценарий M1 и однооперационный Observe/Apply/Verify с обязательными journal/ownership портами по [ADR 0010](adr/0010-operation-boundaries.md), а также конфигурационный граф с фиксированными зависимостями, бюджетами и привязкой плана к журналу по [ADR 0020](adr/0020-configuration-plan-recovery.md). Образцы qBittorrent/Radarr проверяются на fixtures; файловый журнал и remote ownership/lock проверяются отдельными процессными и стендовыми пробами. Полная durability, ContractTests и интегрированная установка ещё не приняты. Первый read-only compiler конкретного qBittorrent preview по [ADR 0021](adr/0021-qbittorrent-installation-plan.md) перечисляет ресурсы и перепроверяет снимки, но ещё не создаёт исполняемый граф и не подключён к экрану #50. Developer tools расположены в `tools/`, исследовательский профиль — в `profiles/`.

```text
src/
  HhHomelab.Wizard.Domain/
  HhHomelab.Wizard.Application/
  HhHomelab.Wizard.Infrastructure/
  HhHomelab.Wizard.Desktop/
tests/
  HhHomelab.Wizard.UnitTests/
  HhHomelab.Wizard.ContractTests/
  HhHomelab.Wizard.DesktopTests/
  fixtures/
profiles/
  hh-homelab/1.3.0/
docs/
  adr/
  testing/
```

| Слой | Ответственность |
| --- | --- |
| Domain | План, ресурсы, зависимости, роли, проверки, правила готовности; без UI и транспорта |
| Application | Сценарии, построение и выполнение плана, запросы интерактивного ввода, интерфейсы адаптеров |
| Infrastructure | SSH/SFTP, HTTP/WebSocket, наблюдение DSM/Docker, профили, журнал и защищённое хранение |
| Desktop | Avalonia Views, ViewModels, навигация, валидация, отображение событий; связывание зависимостей в composition root |

Основные модели: `InstallationProfile`, `InstallationRequest`, `ObservedState`, `InstallationPlan`, `InstallationOperation`, `StepResult`, `EntityRole`, `SecretReference`, `JournalCheckpoint`, `VerificationReport`. Конкретные имена уточняются при реализации; модель должна представлять неопределённый результат внешней операции и ожидающее действие пользователя.

Основные границы: провайдер профилей, инспектор NAS, SSH/SFTP, управление Compose, клиенты сервисов Media, клиент HA, реестры сущностей, журнал, хранилище секретов и источник запросов пользователю. Не нужен универсальный framework для любых установщиков: адаптеры должны обслуживать реальные сценарии этого профиля.

ViewModels используют async-команды с отменой; установка выполняется в Application. Views не содержат shell-команды, HTTP-запросы или правила сопоставления сущностей. Смена экрана не уничтожает работающую сессию. Обновление observable-состояния возвращается в поток UI через границу представления.

## 5. Движок операций и восстановление

Каждая операция описывает ресурс, зависимости, предварительные условия, действие, способ проверки, таймаут, допустимый повтор, компенсацию и последствия отмены. Независимые чтения можно выполнять параллельно; изменения одного ресурса и зависимые шаги выполняются последовательно.

Необходимые состояния: запланировано, выполняется, ожидает пользователя, выполнено, пропущено по профилю, ошибка, прервано, результат неизвестен, компенсируется, компенсировано. Пропущенный обязательный шаг не считается успешным.

Перед изменением записываются намерение, идентичность ресурса и наблюдённое состояние. После действия — проверенный результат. Журнал обновляется атомарно, имеет версию схемы и не содержит секретов. Нужны локальный журнал и минимальный маркер владения на NAS: потеря связи или перезапуск компьютера не должны превращать собственную установку в неизвестный чужой стек.

После восстановления связи мастер заново наблюдает состояние. Потеря HTTP-ответа после создания пользователя или config entry не разрешает повторное создание: сначала проверяется, произошло ли изменение. Сессия блокируется от конкурентного запуска другого экземпляра; оставшийся после аварии lock проверяется, а не удаляется вслепую.

Отмена прекращает дальнейшие действия, но уже отправленная серверу операция может завершиться. Для остановки контейнера, восстановления файла или удаления созданной записи нужна отдельная описанная компенсация. Полного транзакционного отката DSM и внешних устройств нет.

Удалять можно только подтверждённые ресурсы этой сессии в проверенных границах. Медиатека, чужие данные и более поздние ручные изменения сохраняются. Восстановление конфигурации проверяет идентичность и контрольную сумму текущего файла. Секреты после перезапуска вводятся заново, если безопасное локальное хранилище недоступно.

## 6. Этапы разработки

### M0. Проверка контрактов и уточнение профиля

**Цель:** доказать осуществимость первичной настройки на выбранных версиях до разработки всех экранов. Зависимостей от других этапов нет.

Подтверждённая база M0: C#-контракты и disposable harness Media и HA; результаты тестов берутся из протоколов/CI, не поддерживаются числом в плане. HaDockerProbe подтверждает владельца/onboarding, токены, HTTP/WebSocket, реестр и тестовую панель. HTTP проходит pending → restart → reconnect → проверка → promote; потеря ответа не вызывает повтор записи. Первый [config flow Jellyfin](m0/JELLYFIN_FLOW.md) проверяет credentials, loaded entry/server identity и неизвестный исход создания.

[Доставка Monitor Docker и рендер локального профиля](m0/HA_LOCAL_PROFILE.md) проверяют происхождение компонента, полный YAML и десять template cases. [Серверный запуск](m0/HA_RUNTIME.md) проверяет 40 Docker entities, синтетические метрики, настоящий Socket Proxy, отказы, уведомление, restart и 18 ускоренных сценариев Script. DSM/плееры остаются Missing; реальные устройства, время и playback не подтверждены.

Добавлены [read-only реестры, технический план десяти ролей и enable выбранной identity](m0/HA_ENTITY_ROLES.md). DSM определяется по точным metric/API/unique IDs и родительским устройствам, плееры выбираются явно. Настоящий HA подтвердил enable helper, restart requirement, потерю ответа без повторной записи и live state после restart. DSM остаётся fixture/source evidence; общего apply/recovery engine для всех ролей пока нет.

Добавлены [USER flows DSM/LG/Android TV/Cast](m0/HA_DEVICE_FLOWS.md) с явными credentials/OTP/backup/confirmation/PIN шагами, проверкой конфликтов и запретом повторов неизвестной записи. Нативный стенд подтвердил initial forms, LG confirmation form, DSM OTP/backup serializer на синтетической share, loaded Cast и restart. Полное сопряжение и физическая идентичность устройств не подтверждены.

Добавлены [выбор native discovery flow и проверка технической привязки](m0/HA_DISCOVERY_BINDING.md): explicit selection, повторная проверка source/unique ID/step, продолжение исходного flow и read-only entry/device/identifier verifier. Нативные формы/progress serializer и Cast/Android identifiers проверены на синтетических данных; фактическое сопряжение и registry identity оборудования требуют аппаратных испытаний.

Для полной приёмки M0 остаются активация/показания DSM, аппаратная привязка, анализ зависимостей лишних плееров, полный dashboard и дополнительные Media-контракты пользователя/policies Jellyfin, transcoding, Arr/indexers. Journal и общий apply/recovery реализуются в M3/M5; контрактные неизвестные не считаются закрытыми. [Протокол проб](m0/PROBE_REPORT.md) фиксирует фактический объём; движок установки ещё не создан; демонстрационный UI M1 работает на искусственном адаптере.

Работы:

1. Сопоставить каждый шаг исходной документации Media/HA с операцией мастера: автоматически, с действием пользователя, исключён по объёму или пока неподдерживаем. Проверить Compose, YAML, шаблоны панели, секреты и реальные зависимости.
2. На изолированном стенде проверить API первого запуска и авторизации qBittorrent, Prowlarr, Radarr, Sonarr, Jellyfin и Seerr. Отдельно проверить временный пароль qBittorrent, создание аккаунтов, повторный запрос после потери ответа и получение API-ключей.
3. Проверить onboarding/auth HA Container, config flows, реестр сущностей, доступную загрузку панели, HTTP-настройки и требуемые права. Не использовать Supervisor или ручное изменение `.storage`.
4. Установить способ доставки Monitor Docker: закреплённый компонент напрямую или HACS с интерактивной авторизацией. Проверить зависимости, происхождение файлов и лицензии.
5. Подготовить схему профиля, искусственные fixtures, матрицу версий и ADR по архитектуре, журналу, секретам и способу установки компонентов. Из старого standalone-выравнивателя использовать проверенные правила только после аудита и тестов.
6. Зафиксировать минимальные сборки Windows 11 x64 для испытаний и проверить SSH/Docker/Compose на DS725+ с DSM 7.4.1-90080. Не заменять сообщённую владельцем версию предположением о возможностях DSM.

**Результат:** таблица покрытия исходной инструкции, минимальные пробы адаптеров, профиль совместимости, список конкретных препятствий и интерактивных шагов.

**Приёмка:** обязательные сервисы имеют подтверждённый путь первичной настройки; неизвестные API-контракты не помечены готовыми. Если необходимый шаг недоступен программно, есть воспроизводимый интерактивный путь внутри сценария и согласованное ограничение. План первого выпуска пересматривается до обещания полной автоматизации.

### M1. Каркас Avalonia/MVVM и воспроизводимая сборка

**Зависимость:** решения M0 по архитектуре и версиям.

**Выбранный интерфейс:** «Фокус», [ADR 0005](adr/0005-focus-ui.md). Центральная колонка, горизонтальная последовательность этапов, одно основное действие и раскрываемые технические подробности. Новое задание владельца разрешило реализацию после выбора макета; приёмка этапа остаётся открытой.

[ADR 0004](adr/0004-m1-entry.md) фиксирует условия начала отдельно от полной приёмки M0. Первый каркас M1 добавляет Application/Desktop, закреплённые пакеты и демонстрационный сценарий; аппаратные проверки и дополнительные API-контракты M0 продолжаются отдельно. M0 этим не закрывается.

Создать solution, четыре основных проекта, DI, базовую навигацию и общий формат ошибок. Закрепить SDK, пакеты и lock-файлы; включить nullable и анализаторы. Реализовать демонстрационный сценарий установки на искусственном адаптере без обращения к NAS: валидация, ход операций, ожидание пользователя, ошибка, отмена.

**Выполнено первым инкрементом:** четыре слоя, DI, MVVM/compiled bindings, темы «Фокус», четыре экрана, валидация, ожидание подтверждения, успех/ошибка/неизвестный исход, отмена и защита от повторного запуска. Добавлены 15 проверок сценария и 8 UI-проверок, native Win32/X11/Wayland probe и проверка fallback, CI self-contained публикация для Windows/Linux, лицензии и реальные команды разработки. [Протокол M1](m1/README.md) отличает локальные результаты, автоматические пробы и обязательную клиентскую приёмку.

**Клиентская приёмка:** владелец полностью подтвердил PR #110 / cac10f0 на Windows 11 26H1 и Ubuntu 24.04.4 LTS / GNOME X11 и Wayland; [протокол](m1/2026-10-18-owner-check.md) фиксирует завершение #42–#45. Автоматические Xvfb/Weston и Windows Server runner сохраняют отдельный уровень доказательств. Текущая готовность этапа и оставшийся аудит — в [STATUS](STATUS.md).

**Приёмка:** окно запускается на Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland без установленного .NET; команды не зависают, повторное нажатие не запускает вторую сессию; UI не зависит от конкретных API. Системные зависимости Linux проверены и документированы. Это демонстрационный каркас, ещё не установщик NAS.

### M2. Подключение, preflight и конкретный план

**Зависимость завершения:** полная приёмка M0, M1. Разработка портов/design/fixtures и одноразовый SSH/Docker стенд разрешены раньше по [ADR 0008](adr/0008-audit-development-sequence.md); аппаратный протокол и полная приёмка остаются отдельными.

Реализовать SSH-аутентификацию паролем/ключом, проверку host key, SFTP и определение возможностей `sudo` без передачи секретов в аргументах процессов. Проверить DSM, архитектуру NAS, Container Manager/Docker/Compose, место, время, занятые порты и ресурсы. Неподготовленный NAS получает инструкции по prerequisite; мастер не устанавливает DSM и не меняет сеть.

Проверить абсолютные пути после разрешения symlink, DSM ACL, UID/GID и доступ контейнеров к каталогам. Существующая медиатека допустима; существующие базы приложений и чужие контейнеры блокируют новую установку. Согласованную структуру общей `/data` проверить для qBittorrent/Radarr/Sonarr, включая возможность hardlink на одной файловой системе.

Компилятор профиля должен различать три адресных контекста: компьютер → NAS, HA на NAS → локальный сервис, контейнер → имя сервиса в Compose-сети. Изменение `BIND_ADDR` не должно ломать мониторинг, ожидающий loopback. Docker Socket Proxy и FlareSolverr не публикуются в LAN ради исправления связи.

**Приёмка:** до изменений показан список конкретных ресурсов и проверок; неправильные пути, права, секреты, конфликты и адреса останавливают соответствующий шаг. Проверка не модифицирует NAS скрыто. При изменении окружения готовый план перепроверяется.

### M3. Выполнение, журнал и продолжение

**Зависимость завершения:** M2. Модель операций #99 и минимальные инкременты журнала/executor/доставки #51–#54 разрабатываются до полного M0/M1 на fixtures и одноразовом стенде; первый вертикальный результат — #101. К реальной установке требования M3 применяются полностью.

Реализовать граф операций, блокировки, таймауты, отмену, журнал намерений и подтверждений, маркеры владения, резервные копии создаваемой конфигурации. Передавать файлы через временный путь с проверкой содержимого и атомарной заменой. Отделить наблюдение от изменения и проверку результата от успешного ответа транспорта.

Обработать обрыв SSH, потерю ответа API, остановку приложения, повторный запуск, ожидание PIN, изменение файла пользователем и несовместимую схему журнала. Разрешать продолжение только для доказанно собственной сессии. Для каждой мутации указать доступную компенсацию или невозможность безопасного отката.

Первый локальный инкремент журнала: [ADR 0011](adr/0011-local-file-journal.md) и [протокол process-restart](testing/2026-10-18-file-journal.md). Он использует порты #99; до реальных мутаций требуются remote ownership/lock, проверенная crash durability и host/preflight. Локальная блокировка одного каталога не заменяет координацию нескольких компьютеров.

**Приёмка:** инъекция сбоя до/после каждого существенного внешнего изменения не создаёт дубликатов, не удаляет медиатеку и позволяет понять состояние. Повторный экземпляр не изменяет те же ресурсы. Невозможный откат явно отражён в отчёте. M3 обязателен до установки реального стека.

### M4. Установка и первичная настройка Media

**Зависимость:** M0, M2, M3.

1. Создать только согласованные каталоги конфигурации и медиаструктуру; проверить права без рекурсивной смены владельца всей медиатеки.
2. Сформировать `.env`/Compose из закреплённого профиля, проверить конфигурацию без вывода секретов, запустить семь сервисов. Проверить readiness каждого, а не только состояние контейнера.
3. Настроить qBittorrent: первоначальный доступ, постоянные credentials, пути и отдельные категории фильмов/сериалов. Обработать повторный запуск и временную аутентификацию.
4. Настроить Radarr/Sonarr: аутентификацию, корневые папки, клиент загрузки, категории, доступные профили качества и параметры, выбранные пользователем. Не переносить категории фильмов на сериалы.
5. Настроить Prowlarr: связи с обоими Arr, пользовательский выбор индексаторов, проверку доступа и применимость категорий; FlareSolverr только там, где выбранному источнику нужен proxy. API-ключи передаются по нужному адресному контексту.
6. Пройти первичную настройку Jellyfin: аккаунт, библиотеки и доступы. Настроить Seerr: аккаунт и связи с Jellyfin, Radarr и Sonarr. Подтвердить тестами работоспособность связей.
7. Проверить импорт и воспроизведение предоставленного пользователем тестового файла. Проверку реальной загрузки запускать отдельным понятным действием с выбранным пользователем материалом.

**Приёмка:** нет незащищённого временного доступа после настройки; приложения видят ожидаемые папки и друг друга; фильм и серия имеют правильные категории и маршруты импорта. Мастер не добавляет индексаторы и не запускает загрузки без выбора пользователя. Повторное продолжение не создаёт вторые аккаунты, библиотеки или download clients.

### M5. Установка и первичная настройка Home Assistant

**Зависимость:** M0, M3, M4 для связей с Media.

Подготовить отдельный Compose-проект HA Container и read-only Docker Socket Proxy; проверить loopback-привязку и разрешённые операции proxy. Создать конфигурацию и секреты по профилю, запустить HA, пройти onboarding владельца и получить локальную авторизацию подтверждённым способом.

Компилятор конфигурации должен исключать выключенные облачные и опциональные модули вместе с зависимыми сценариями, секретами и карточками. Нельзя сохранять сломанные ссылки или выдуманные credentials ради запуска. Адреса NAS/HA и координаты берутся из ввода, а не примеров upstream. HTTP-параметры применяются способом, поддерживаемым выбранной версией HA.

Установить закреплённый Monitor Docker. Создать config entries Synology DSM, LG webOS, Android TV Remote, Google Cast, Jellyfin и требуемых локальных интеграций Media через проверенные flows/API. На LG дождаться подтверждения, на GX1 — PIN, для Jellyfin-клиента попросить запуск приложения. Неполный flow сохраняет состояние и не создаётся заново вслепую.

**Приёмка:** HA перезапускается и загружает сформированные модули без ошибок конфигурации; интеграции соответствуют нужным устройствам и сервисам. Необходимое действие пользователя обозначено явно. Отсутствие HACS-авторизации или неподключённый телевизор не превращаются в фиктивно успешную установку.

### M6. Сущности, роли устройств и панель

**Зависимость:** M5.

Построить инвентаризацию реестров и фактических состояний. Для DSM сопоставлять NAS, техническую метрику, unique_id, том и слот диска; включать нужные отключённые сенсоры через реестр и проверять появление после reload. Обязательные метрики исходного профиля: CPU total, real memory, температура, последний запуск, заполнение тома 1, состояние дисков 1 и 2. Если структура NAS отличается, требуются проверенный выбор и адаптация профиля.

Назначить роли LG TV, Android TV Remote GX1, Cast GX1 и Jellyfin GX1, а также remote GX1. Проверять домен, интеграцию и устройство, а не выбирать первый плеер. Конкретные `entity_id` получать из профиля автоматизаций и панели. Коллизии идентификаторов и изменение идентичности между планом и применением блокируют переименование; промежуточные имена и журнал позволяют безопасно менять цепочки.

Для сущностей без редактируемого unique_id, включая возможные Monitor Docker, проверять соответствие имени в конфигурации, а не обещать переименование через реестр. Для лишних плееров сначала составить зависимости статических и динамических ссылок. Использовать отдельные действия «убрать с панели», «скрыть» и «отключить»; скрытие не гарантирует исчезновение из всех списков выбора. Неизвестная зависимость запрещает автоматическое отключение.

Установить панель с явными ролями и набором карточек, проверить сохранение и загрузку. Если пользователь выключил необязательную функцию, её карточки и зависимые сценарии корректно исключаются.

**Приёмка:** обязательные ссылки разрешаются на правильные сущности; показания DSM различают disabled/отсутствие/ожидание/unavailable. Панель и используемые списки выбора проверены отдельно. Дополнительные плееры не отключены ценой поломки Jellyfin, Cast или автоматизаций.

### M7. Функциональная проверка и отчёт

**Зависимость:** M4–M6.

Проверки выполняются в несколько уровней: синтаксис и загрузка конфигурации; контейнеры и API; реестры и свежесть измерений; реальные связи приложений; выбранные пользователем действия на устройствах. Проверять HA можно через конфигурационный механизм закреплённой версии и реальные ошибки загрузки; ответ health endpoint не заменяет эти проверки.

Для Media проверить доступ от каждого потребителя, пути импорта, hardlink на разрешённом тестовом файле, библиотеки и запросы Seerr. Для HA проверить DSM, Monitor Docker, управление LG/GX1 по запросу пользователя, наблюдение Jellyfin/YouTube и зависимости автоматизаций. Android TV Remote `app_id` сам по себе не доказывает воспроизведение.

Ночную автоматику сначала проверить на искусственных последовательностях состояний: начало/пауза/остановка Jellyfin, просмотр YouTube, недостоверное состояние, перезапуск HA, ручное изменение режима, временная недоступность и задержка события. Затем провести реальные согласованные проверки без принудительной подмены production-состояний. Не включать телевизор и не запускать ночное выключение скрыто.

Датчик, ещё не получивший первое показание, отображается как ожидающий с учётом интервала обновления, а не как исправный или отсутствующий. Отчёт содержит профиль и версии, результаты каждого уровня, обязательные оставшиеся действия, ограничения и очищенную диагностику; credentials исключены.

**Приёмка:** заявленная готовность подтверждается наблюдениями и сценариями на NAS. Ошибки обязательных функций не скрываются агрегированным зелёным статусом. Отключённые облачные функции не нужны для успеха локального профиля. Mock/fixture-проверки отмечены отдельно от аппаратных.

### M8. Испытания и выпуск

**Зависимость:** M7.

Провести полный сценарий новой установки и продолжения после сбоев отдельно с Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland на согласованной DS725+ / DSM 7.4.1-90080. Зафиксировать фактически наблюдённые версии клиентских ОС, DSM, Docker/Compose, HA и всех адаптеров. Тестовый NAS/каталоги выбираются заранее; действующая установка не очищается ради испытания.

Подготовить self-contained пакеты Windows/Linux, перечень Linux-зависимостей, контрольные суммы, требуемые лицензии и сведения о сторонних компонентах. Проверить запуск на чистых клиентских машинах без SDK/runtime, обновить инструкции, troubleshooting и CHANGELOG. Подписанные пакеты зависят от доступности ключей/сертификата: неподписанный выпуск нельзя описывать как подписанный.

**Приёмка:** все обязательные сценарии первого выпуска подтверждены; известные ограничения опубликованы; пакеты воспроизводимо собираются и запускаются на заявленной матрице. Только после этого создаются tag и release мастера. Документация сама по себе не основание объявлять 1.0.0.

### После первого выпуска

Отдельные этапы: диагностика/исправление существующего стека, обновления профиля и установленной системы, обычный Linux-сервер, дополнительные устройства и облачные функции. Для них нужны собственные требования к владению ресурсами, миграциям и восстановлению; они не добавляются скрыто в MVP.

Для **2.0.0 мастера** принят отдельный объём: полностью настраиваемый состав стека и перевод hh-homelab в архивное состояние после переноса необходимых материалов. Подробности и критерии перехода приведены в разделе 12. Это не меняет обязательный состав первого выпуска и не означает, что ремонт установленной системы, Linux-сервер или облачные функции автоматически входят в 2.0.0.

## 7. Последовательность и промежуточные версии

Цепочка полной приёмки: **M0/M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8**. Начало демонстрационного M1 отделено от полной M0 в [ADR 0004](adr/0004-m1-entry.md). После аудита независимые design/fixture и одноразовые стендовые инкременты M2/M3 также разрешены до полной M0/M1 по [ADR 0008](adr/0008-audit-development-sequence.md). Это не меняет критерии завершения этапов; реальная установка требует обязательных механизмов M3 и авторизованного конкретного плана.

Рабочий приоритет после аудита:

1. #97: B1/B2, deadline/cancellation и безопасная классификация HTTP; регрессия перед объединением транспорта.
2. #99 и #100: Domain-модели/исходы и порты Application, согласованность pins/roles/profile. Долговечное намерение принадлежит #51.
3. #101: один qBittorrent через SSH/preflight/план/журнал/verify и resume в новом процессе на одноразовом стенде; использовать минимальные инкременты #46–#54.
4. #98: читаемость/formatter/Dependabot/coverage отдельными PR; #103: screen VM/interaction/validation до настоящих экранов; #102: HA responsibilities и probe helpers до M5.

Новые HA-контракты вширь уступают обратной связи вертикали. Клиентская #42–#45 и аппаратная #35–#40 приёмка продолжаются отдельно и остаются обязательными. Полный data-driven состав V2 не переносится в v1; его pins/roles/transforms и параметры устройств готовятся сейчас. [Реестр аудита](audit/2026-10-11-follow-up.md) связывает каждую находку с задачей и доказательством.

Предложение для будущих промежуточных версий, а не объявленные выпуски:

| Версия | Результат |
| --- | --- |
| 0.1.x | Каркас, демонстрационный режим, подключение и preflight; полноценных установок ещё нет |
| 0.2.x | Media с первичной настройкой и восстановлением |
| 0.3.x | HA, интеграции, сопоставление сущностей и панель |
| 0.4.x / beta | Сквозные проверки, аппаратные испытания, устранение ограничений |
| 1.0.0 | Полный согласованный сценарий принят на Windows 11 и Ubuntu / X11 и Wayland |
| 2.0.0 | Выбор компонентов и согласованных связей; самостоятельные профили wizard; hh-homelab переведён в архив после выполнения критериев раздела 12 |

Оценка сроков выполняется после M0: неизвестные onboarding/config flow API и доступ к испытательному NAS влияют сильнее, чем количество экранов. Неподтверждённые сроки не включаются в обещания выпуска.

| HA-автоматизации | Jellyfin/YouTube, задержки и недостоверные состояния, ручные действия, перезапуск, исключённые функции | Unit сценариев + аппаратная проверка |
| Выпуск | Чистая клиентская ОС, отсутствие .NET, Linux-библиотеки, лицензии, контрольные суммы | Клиентская матрица + DS725+ |

Unit-тесты не требуют NAS. Contract-тесты доказывают формат и поведение API выбранных версий, но не DSM ACL или сопряжение физического ТВ. Аппаратные результаты сохраняются в `docs/testing/` после испытаний с датой, версией, сценарием и ограничениями. Незапущенный тест имеет статус «не проверено».

## 9. Готовность первого полноценного выпуска

- Есть рабочие пакеты, проверенные отдельно на Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland без отдельной установки .NET.
- Новая установка на DS725+ разворачивает семь Media-сервисов и два контейнера HA; приложения настроены и связаны, а не просто запущены.
- Пользователь выбирает индексаторы, параметры и доступы; сопряжение проходит через понятные интерактивные шаги.
- Обязательные DSM-сенсоры и роли устройств согласованы с автоматизациями; панель работает, дополнительные плееры обработаны с проверкой зависимостей.
- Локальные сценарии Jellyfin/YouTube проверены. Исключённые облачные модули не оставляют ошибочных ссылок.
- Прерывание и продолжение не создают дубликаты, не стирают медиатеку и не перезаписывают чужие изменения.
- Секреты отсутствуют в логах, журналах и support bundle; доверие SSH/TLS проверяется.
- Отчёт отделяет готовность, ожидание пользователя, ограничения и непроверенные функции.
- Документы соответствуют фактическому поведению; опубликованы проверенная матрица и результаты аппаратных испытаний.

## 10. Риски и решения до соответствующего этапа

| Риск | Действие |
| --- | --- |
| API первого запуска меняется между версиями | Закрепление профиля, контрактные пробы M0, отказ от непроверенных версий |
| Частично выполненное изменение при потере ответа | Журнал намерений, проверка фактического состояния, запрет слепого повтора |
| DSM ACL и filesystem отличаются от обычного Linux | Наблюдение на NAS и аппаратные тесты; никакой массовой смены прав |
| Discovery недоступен с компьютера пользователя | Проверка доступности с NAS/HA, ввод адреса и идентичности, без перенастройки сети |
| Jellyfin entity появляется только при активном клиенте | Ожидание пользователя, запуск приложения, повторное наблюдение вместо фиктивной сущности |
| Удаление лишних плееров ломает динамические ссылки | Анализ зависимостей и выбор ролей; неизвестные зависимости блокируют отключение |
| Неподключённый опциональный модуль ломает YAML | Компиляция модулей и всех зависимостей, проверка конфигурации M5/M7 |
| Linux-пакет собран, но не запускается на рабочем столе | Проверка чистой Ubuntu в X11 и Wayland, системных библиотек и реального backend до выпуска |

Выбор клиентских ОС согласован: Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland. Инженерные решения — минимальные сборки Windows, конкретные пакеты, SSH-библиотека, хранение credentials, доставка Monitor Docker и формат пакетов — принимаются по результатам M0/M1 с ADR. Их пока нельзя считать реализованными или испытанными.

## 12. Версия 2.0.0: настраиваемый стек и архив hh-homelab

**Статус:** требования добавлены 11 октября 2026 года; реализация и выпуск ещё не начаты. Версия 2.0.0 относится к hh-homelab-wizard, а не к исходному профилю hh-homelab v1.3.0. Работа следует за приёмкой первого полноценного выпуска M8; дату выпуска определяем после оценки и проверки новых контрактов.

### 12.1. Выбор состава установки

Мастер должен позволять собрать стек из поддерживаемого каталога компонентов, показывать назначение каждого компонента и объяснять необходимые зависимости. Набор «полный Media + HA» остаётся готовым вариантом. Пользователь может изменить его перед установкой; скрытое включение необязательных сервисов запрещено.

| Компонент / функция | Требование для 2.0.0 |
| --- | --- |
| Radarr | Опциональная автоматизация фильмов; при выключении исключаются его контейнер, категория, связи и задания проверки |
| Sonarr | Опциональная автоматизация сериалов; не требует выбора Radarr |
| Bazarr | Новый опциональный модуль субтитров; связи только с выбранными Radarr/Sonarr, выбор языков и провайдеров пользователем |
| Home Assistant | Весь модуль можно не подключать: без контейнеров HA/proxy, Monitor Docker, интеграций, сущностей, панели и автоматизаций |
| Jellyfin | Самостоятельный вариант просмотра существующей медиатеки без Radarr, Sonarr, Bazarr и Home Assistant |
| qBittorrent | Опциональный загрузчик; категории зависят от выбранных сценариев, ручные загрузки не требуют Arr |
| Prowlarr | Опциональное управление выбранными пользователем индексаторами; связи только с выбранными Arr |
| Обработчик защиты индексаторов | Выбор одного из FlareSolverr, Byparr, Solvearr, NoFlare или режима «Не использовать»; включение по потребности выбранных индексаторов |
| Seerr | Опциональные запросы контента; фильмовые/сериальные функции и связи соответствуют выбранным Arr и подтверждённым возможностям API |

В пределах каталога поддержать Media без HA, HA без Media и совместную установку. Для HA без Media исключать интеграции, карточки, мониторинг контейнеров и сценарии, зависящие от отсутствующих медиасервисов; независимые сценарии устройств сохранять. Пустой выбор не должен создавать ресурсы и не считается успешной установкой стека.

Каталог описывает `requires`, совместимость, предоставляемые функции и ограничения каждого компонента. Перед установкой валидатор проверяет весь граф, показывает причину недопустимого сочетания и предлагает конкретное изменение выбора. По принятой политике Bazarr требует хотя бы один выбранный совместимый Arr; точные API-контракты, провайдеры, лицензии и версии исследуются до реализации. Bazarr отсутствует в текущем профиле v1.3.0 и не объявляется уже поддержанным. Режимы Seerr и прямые индексаторы без Prowlarr включаются только после проверки контрактов; неподтверждённая комбинация блокируется с объяснением.

#### Выбор обработчика защиты индексаторов

В экран состава стека включить взаимоисключающий выбор **FlareSolverr / Byparr / Solvearr / NoFlare** и отдельный режим **«Не использовать»**. NoFlare — самостоятельный сервис, а не название режима без обработчика. Для одной установки выбирается один обработчик; несколько параллельных обработчиков, автоматическая замена и переключение на другой проект при ошибке в этот объём не входят.

| Вариант | Источник для исследования контракта |
| --- | --- |
| FlareSolverr | [FlareSolverr/FlareSolverr](https://github.com/FlareSolverr/FlareSolverr) |
| Byparr | [ThePhaseless/Byparr](https://github.com/ThePhaseless/Byparr) |
| Solvearr | [nabil-ak/Solvearr](https://github.com/nabil-ak/Solvearr); исходный репозиторий архивирован, план поддержки и сборки требует проверки |
| NoFlare | [Пакет noflare на PyPI](https://pypi.org/project/noflare/), указанный владельцем; [исходный репозиторий bitbytelab/noflare](https://github.com/bitbytelab/noflare), связанный из метаданных пакета |
| Не использовать | Обработчик не разворачивается и proxy-связи не создаются |

Перед включением каждого варианта в устанавливаемый профиль исследовать и закрепить версию, источник образа либо воспроизводимой сборки, digest/контрольные суммы и лицензии. Проверить API и формат ответа, связь с закреплённой версией Prowlarr, применимость к выбранным индексаторам, требования к ресурсам DS725+, таймауты и сохранение состояния после перезапуска. Заявленная upstream взаимозаменяемость не заменяет контрактные и сквозные проверки; пока они не пройдены, вариант остаётся требованием плана, а не доступной рабочей функцией.

Конфигурация содержит только выбранный обработчик: его контейнер, параметры, необходимые тома, адрес в Compose-сети, связь и теги соответствующих индексаторов, операции и проверки. Для HA мониторинг отражает фактическое имя выбранного сервиса. Не публиковать обработчик в LAN ради исправления связи. В режиме «Не использовать» отсутствуют ресурсы и ссылки всех четырёх вариантов; если выбранному индексатору по проверенному контракту нужен обработчик, мастер объясняет ограничение и предлагает изменить выбор индексатора или обработчика.

В журнале фиксировать идентификатор и версию выбранного обработчика; после сбоя продолжать с тем же вариантом. Успешный запуск контейнера или тест API не считать доказательством доступа к конкретному индексатору: отдельно проверять выбранную пользователем связь без запуска загрузки. Не обещать универсальную работоспособность на всех индексаторах.

### 12.2. Генерация конфигурации и работа мастера

1. Добавить экран выбора компонентов и функций с готовыми наборами и ручным выбором. После выбора показывать итоговый состав, связи, каталоги, порты, требования к доступам и действиям пользователя.
2. Генерировать Compose, параметры, секреты, каталоги, категории загрузок, библиотеки, связи приложений, HA YAML и панель из одного разрешённого графа. Неиспользуемые секреты, порты, тома и ссылки не должны попадать в результат.
3. Формировать план операций, ожидания readiness и итоговую проверку только для выбранных функций. Исключённая функция получает статус «не выбрана», а не «ошибка» или фиктивный успех.
4. Настраивать Bazarr по закреплённому контракту: подключение к нужным Arr, языки и провайдеры, сопоставление путей и минимально необходимые права на запись субтитров. Внешние аккаунты и credentials предоставляет пользователь; их создание не входит в этот этап.
5. Сохранять выбор, версию и контрольную сумму профиля вместе с версией схемы журнала. Продолжение прерванной установки использует согласованный состав; изменение выбора требует нового плана и проверки уже созданных ресурсов.
6. Обновить инструкции, troubleshooting, схемы связей и справку под каждый поддержанный вариант. Пользовательские настройки качества, путей и библиотек согласуются с выбранными компонентами.

Обновление приложения не должно самопроизвольно менять состав установленного стека. Удаление работающего сервиса, его базы или файлов при снятии флажка не допускается. Автоматическое изменение состава уже завершённой установки и миграция существующей системы требуют отдельного решения о поддерживаемом объёме; обязательный результат этого этапа — новая настраиваемая установка и продолжение собственной сессии.

### 12.3. Самостоятельные профили и перенос материалов

hh-homelab-wizard становится основным местом разработки установщика, поддерживаемых профилей и инструкций установки. До архивирования hh-homelab:

- Перенести необходимые шаблоны конфигурации, описание сервисов, правила связей, инструкции, troubleshooting и материалы проверки в версионируемые профили и документацию wizard. Сохранить происхождение, исходный commit/tag, авторство и лицензии перенесённых материалов.
- Закрепить версии новых и существующих компонентов и контрольные суммы исходных материалов; не загружать конфигурацию из изменяемого `main` при установке. Поддержать профиль v1.3.0 как воспроизводимую основу первого выпуска.
- Включить необходимые шаблоны и справку в поставку либо в проверяемый выпуск профиля. Отсутствие доступа к старому репозиторию/сайту документации не должно ломать подготовку плана и генерацию конфигурации; скачивание внешних образов и компонентов остаётся отдельной сетевой зависимостью.
- Проверить ссылки, историю решений, лицензии MIT / CC BY 4.0 и сведения о сторонних компонентах. Перенести актуальные открытые задачи или связать их с задачами wizard, сохранив ссылки на исходное обсуждение.
- Опубликовать в hh-homelab уведомление о завершении активной разработки, ссылку на wizard и инструкции для действующих установок. Сохранить историю, теги, выпуски и доступ к прежним инструкциям; проверить размещение документации и состояние автоматических публикаций до архивирования.

### 12.5. Приёмка и условия архивирования

- Проверены варианты: полный Media + HA; Media без HA; HA без Media; только фильмы; только сериалы; оба Arr; Jellyfin без Arr; Bazarr с каждым разрешённым набором Arr. Seerr и Prowlarr проверены включёнными/выключенными в совместимых вариантах.
- Для FlareSolverr, Byparr, Solvearr и NoFlare отдельно проверены генерация конфигурации, совместимые связи с Prowlarr и выбранными индексаторами, readiness, перезапуск и продолжение собственной сессии. Режим «Не использовать» не оставляет контейнеров, томов, proxy-настроек или ссылок мониторинга; конфликт выбора отклоняется до записи на NAS.
- Для каталога выполняются проверки всех правил зависимостей; недопустимые сочетания отклоняются до записи на NAS. Автоматические проверки генерации дополняются сквозными пробами представительных вариантов и аппаратными испытаниями, а не подменяют их.
- Для отсутствующих компонентов нет неработающих ссылок в Compose, секретах, Media API, HA YAML, панели и автоматизациях. При выключенном HA не запрашиваются HA-доступы, сопряжение устройств или параметры панели.
- Для выбранных функций подтверждены первичная настройка, реальные связи, сохранение после перезапуска, отказ при конфликте и продолжение после прерывания без дублей и потери медиатеки. Субтитры проверяются на согласованном тестовом материале.
- Пакеты проверены на Windows 11 x64 и Ubuntu 24.04 LTS x64 / X11 и Wayland с установкой на согласованную DS725+ / DSM. Расширение целевой платформы требует отдельной приёмки.
- Профили и документация доступны из выпуска wizard; проверен сценарий без доступа к исходному hh-homelab. Старые профили и журналы имеют явную политику совместимости, несовместимые сессии не продолжаются вслепую.
- Выпуск 2.0.0 опубликован с результатами испытаний, ограничениями и инструкциями для новых и действующих пользователей; перенос материалов и уведомление в исходном репозитории завершены. После этого владелец переводит **hh-homelab** в архивное состояние; **hh-homelab-wizard** остаётся активным.

Добавление этого плана не выполняет архивирование. Переход в архив не удаляет историю или пользовательские данные, не останавливает уже установленные стеки и не запускает их обновление.
