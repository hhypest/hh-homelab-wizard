# M0: серверный запуск локального профиля HA

`HaRuntimeProbe` запускает полный [локальный профиль](HA_LOCAL_PROFILE.md) в настоящем Home Assistant Container **2026.10.0** вместе с Docker Socket Proxy **v0.5.0**. Monitor Docker устанавливается из проверенного commit и работает без изменений. Это developer tool для проверки контрактов; установщика NAS, GUI, журнала установки и продуктового resume ещё нет. M0 остаётся открытым.

## Стенд и границы доступа

Используются только собственные контейнеры, bridge-сеть и два named volumes с метками владения. HA публикует порт на loopback с динамическим номером; proxy и Docker API не публикуются на хосте. Bind mounts отсутствуют, настоящий `/var/run/docker.sock` не подключается. При остановке/старте и cleanup повторно проверяются идентичность ресурсов и метки. Cleanup имеет отдельный deadline; успешная проба требует его подтверждения. После аварийного завершения процесса долговечный recovery пока отсутствует.

В отдельном контейнере stdlib Python HTTP server обслуживает **синтетический Docker API** через Unix socket собственного volume. Он возвращает девять контейнеров с именами из профиля и заданными метриками. Права socket разрешают доступ процессу настоящего proxy, но не предоставляют доступ к Docker Engine компьютера. GET проходит через штатный HAProxy; проверочный POST остановки синтетического контейнера получает 403. В API нет операций установки или управления реальными контейнерами.

HA получает исходный payload из 50 файлов через TAR/stdin. Пароли и токены существуют в памяти клиента и временном собственном config volume, не попадают в аргументы процессов и отчёт. `secrets.yaml` имеет режим 0600. Источник hh-homelab — v1.3.0, commit `b05047b081f3543520582315002e359ef1d93e59`; проверяются все 19 fingerprints. Исходный checkout и штатные времена YAML не изменяются.

## Наблюдение работающего сервера

После onboarding и проверки владельца проба ждёт RUNNING и выполняет полный `check_config`. `HomeAssistantContractClient.ReadLocalProfileRuntimeAsync` читает `get_config` и `get_states`, не создаёт сущности и возвращает ограниченную модель без credentials, полных attributes, названий медиаматериалов и текстов ошибок proxy.

Наблюдаются:

- 40 Docker entities: версия, общее/работающее число контейнеров, быстрый `docker_down`, а также state/CPU/memory/memory_percent для каждого из девяти контейнеров;
- десять ожидаемых аппаратных entity IDs: пять DSM, четыре плеера LG/GX1/Cast/Jellyfin и remote GX1;
- шесть локальных scripts: включение/выключение ТВ, запуск YouTube/Jellyfin, Jellyfin Resume и локальные уведомления;
- только безопасные признаки error/OOM/restarting быстрого датчика, без сырого текста error.

Модель различает `Missing`, `Unknown`, `Unavailable`, `Invalid` и `Available`. Нулевое показание не приравнивается к отсутствию. Не принимаются NaN/Infinity, отрицательные метрики, дробное/переполненное число контейнеров, memory_percent выше 100 и некорректные состояния контейнеров/scripts. Атрибуты старого результата при `unknown`/`unavailable` не подтверждают исправность proxy.

Первое CPU остаётся `Unknown`: компоненту нужны два измерения, а исходный часовой scan interval сохранён. Проба подтверждает синтетические memory **64 MiB**, memory_percent **25%** и число контейнеров **9**, создание всех выбранных Docker entities и загрузку Monitor Docker. Это проверка преобразования данных, а не измерение настоящего NAS. Аппаратные сущности остаются `Missing`; фиктивные DSM и плееры в сервер не добавляются.

Быстрый датчик проверяется при остановке контейнера, OOM, restarting, повреждённом JSON, HTTP 503 и восстановлении. Отдельно останавливается и запускается настоящий proxy, подтверждается ошибка и последующее восстановление. Проверка GET готовности начинается ещё при остановленном proxy; через две секунды он запускается. Временный отказ соединения допускает повтор с общим deadline 30 секунд, timeout запроса 2 секунды и интервалом 0,25 секунды. POST-проверка выполняется один раз после готовности и требует 403. Отмена/ошибка запуска отменяет и дожидается фоновой проверки. Локальное уведомление вызывается через API HA и проверяется через `persistent_notification/get`.

После перезапуска HA профиль и метрики проверяются повторно. Старый token заранее отзывается; новый клиент использует повторно определённый loopback port и подтверждает login/owner. Отзыв новой сессии и cleanup обязательны.

## Динамические сценарии автоматизаций

Внутри образа выполняется настоящий `homeassistant.helpers.script.Script` выбранной версии с последовательностями из исходного YAML. Проверяются схема и action config. Для каждого случая создаётся отдельный HA-контекст с синтетическими состояниями и зарегистрированными тестовыми сервисами устройств. Он отделён от работающего сервера и не обращается к телевизору, DSM или Jellyfin.

Только в глубокой тестовой копии последовательностей delay сокращён до 0,03 секунды, timeout — до 0,3 секунды. Состояния меняются во время реального ожидания Script; отмена вызывает его `async_stop`. Исходные условия и действия сохраняются. Выполняются **18 случаев**:

| Область | Случаи и ожидаемое поведение |
| --- | --- |
| Ночное выключение | Подтверждённая пауза допускает выключение GX1, затем LG; ошибка toast не ломает этот порядок |
| Пауза и показания | Игнорируемая/ошибочная пауза, потеря источника и unavailable во время предупреждения предотвращают выключение |
| Изменение состояния | Возобновление просмотра, защита во время предупреждения или grace, окончание просмотра во время предупреждения предотвращают выключение |
| Ручной запрет | `tv_no_auto_off` блокирует действия до pause |
| Отмена | Остановка Script во время предупреждения и grace предотвращает выключение |
| Jellyfin Resume | Подтверждённый media ID приводит к play, затем seek на 12,5 секунды; другой ID не допускает seek |
| Отказы Resume | Нет сессии, устаревшие данные и неудачный запуск приложения предотвращают play/seek; для запуска проверяются три попытки |

Эти сценарии проверяют ветвления и прерывания в движке Script. Они не доказывают реальные многоминутные интервалы, срабатывание time triggers в нужный час, доставку команд устройствам, actual playback/seek или восстановление незавершённого Script после рестарта HA. Эти проверки остаются до аппаратной приёмки.

## Воспроизведение

Нужны SDK 10.0.401, Linux Docker Engine и checkout точного hh-homelab commit. Python на компьютере не нужен: фиксированные fixture-программы исполняются внутри образа HA.

```sh
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
docker pull ghcr.io/home-assistant/home-assistant:2026.10.0
docker pull ghcr.io/tecnativa/docker-socket-proxy:v0.5.0
dotnet run --project tools/HhHomelab.Wizard.HaRuntimeProbe --no-build --configuration Release -- /path/to/hh-homelab-v1.3.0
```

CLI принимает только путь к исходному checkout. Он не принимает адрес NAS и не устанавливает стек на существующую систему. Внешний deadline — 12 минут; Ctrl+C прекращает ожидание, затем запускает независимый cleanup. Журнал содержит фиксированные этапы и безопасные коды, без сырых Docker/HA logs.

11 октября 2026 года два свежих локальных прогона на Windows / Docker Desktop Linux Engine 29.8.2 завершились exit 0 с 18 action cases, restart, session revocation и cleanup. Locked restore, Release build и 343 unit/fixture-теста прошли. CI job `ha-local-runtime` на Ubuntu 24.04 повторяет пробу дважды; результат конкретного CI run фиксируется в PR.

Далее нужны остальные config flows, активация и рабочие показания DSM после reload, выбор конкретных устройств, проверка зависимостей лишних плееров и полный dashboard. Проверка прав обычного пользователя Jellyfin, фактических показаний DSM, реального времени, управления и воспроизведения выполняется отдельно. Проба не превращает отсутствующую интеграцию в готовую.
