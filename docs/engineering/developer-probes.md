# Инструменты разработчика и изолированные пробы

Тип: действующая инструкция для разработчика; команды, изоляция стендов и пределы доказательства developer tools.

[Документация](../README.md) · [Разработка](../development.md) · [Проверки](testing.md) · [Сводка M0](../verification/m0.md)

Инструменты из `tools/` — не операции готового установщика. Они проверяют контракты на fixtures и одноразовых стендах; их нельзя запускать на NAS как установщик. Число тестов и результаты конкретных запусков фиксируются в протоколах и отчётах CI, а не здесь. Пробы SSH/Docker-стенда (SshDockerProbe), локального журнала (JournalProbe) и полного HA-сервера описаны в [протоколах](../catalog.md#протоколы-конкретных-проверок) и [контракте HA runtime](../contracts/ha-runtime.md).

## QbProbe: диагностика авторизации qBittorrent

QbProbe — дополнительная диагностическая программа для API **5.2.4**. После сборки запускается с единственным аргументом base URL с завершающим `/`; две строки stdin — username и password. Секреты нельзя помещать в аргументы команд, историю shell, Git или перенаправлять в сохраняемый файл. Программа создаёт отдельный HTTP-клиент с пустыми cookies и отключёнными redirects. Сначала читает защищённый endpoint версии: ожидается 403. Если версия доступна до login, проверка останавливается с `qb.authentication.context-preauthenticated`: существующая сессия или обход авторизации не позволяют проверить пароль. Инструмент не завершает чужую сессию и не изменяет политику авторизации сервера.

После preflight выполняются login и повторное чтение версии; QbProbe не изменяет настройки сервиса. При использовании `QbittorrentContractClient` из кода HTTP-клиент должен принадлежать только этой пробе; параллельная авторизация и изменение bypass-политики во время проверки недопустимы. Отдельный QbDockerProbe ниже проверяет настройку на disposable стенде.

| Код диагностики | Значение / следующий шаг |
| --- | --- |
| `qb.authentication.context-preauthenticated` | Доступ был открыт до передачи credentials; использовать новый клиент и адрес, для которого авторизация обязательна |
| `qb.authentication.preflight-failed` | Preflight вернул неожиданный HTTP-статус; проверить адрес, proxy и правила HTTP-доступа |
| `qb.authentication.rejected` | Login вернул 401; проверить credentials и HTTP-политику сервера |
| `qb.authentication.forbidden` | Login вернул 403; возможны бан клиента или запрет доступа, это не доказательство неверного пароля |
| `qb.authentication.http-error` | Другой статус login, включая 200 старого API, 404, redirect и 5xx; проверить endpoint и контракт версии |
| `qb.version.unavailable` / `qb.version.unsupported` | Последующий запрос не подтвердил доступ или закреплённую версию |

Для HTTP-ошибок выводится числовой статус; URL, credentials и response body не выводятся. Успешный `v5.2.4` означает, что полный путь проверки завершён; отказ preflight никогда не выдаётся за проверку пароля.

## Проверка формы версий образов

Валидатор образов допускает явные теги версий с двумя–четырьмя числовыми частями, необязательным `v`, числовым `alpha`/`beta`/`rc` или суффиксами упаковки профиля (`ubu2604`, `_v2.0.15`, `-ls479`). Плавающие каналы вроде `latest2`, `stable2026` и `1.2-latest2` отклоняются и для образов, и для Docker mods. Это проверка формы версии, а не доказательство неизменности registry tag. Digest-ссылки пока не поддерживаются этой схемой; наблюдённые digests хранятся отдельно в image evidence.

Проверки ядра CI запускаются на Windows runner и Ubuntu 24.04. Добавлено отдельное задание `qb-runtime` на Ubuntu с двумя запусками QbDockerProbe на свежих контейнерах. Результат конкретного запуска проверяется в Actions; наличие workflow не доказывает его успех. Эти проверки не заменяют испытания GUI на Windows 11, X11/Wayland или работу DSM.

## QbDockerProbe: повторяемая проба qBittorrent

Нужны локальный Docker с Linux Engine и SDK из global.json. Это developer tool для изолированного тестового окружения; его нельзя запускать на NAS как установщик. Удалённые Docker contexts и `DOCKER_HOST` запрещены. Образ должен быть заранее загружен; инструмент сам не скачивает образы или Docker mods:

```text
docker pull lscr.io/linuxserver/qbittorrent:5.2.4_v2.0.15-ls479
dotnet run --project tools/HhHomelab.Wizard.QbDockerProbe --no-build --configuration Release -- profiles/hh-homelab/1.3.0/research-profile.json
```

Инструмент принимает только исходную версию/commit и образ профиля v1.3.0. Создаёт уникальные container/network/config volume с меткой сессии, без host bind mounts. `/data` — временный tmpfs; порт публикуется только на loopback. Каталоги и конфигурации существующего стека не используются. Сеть — отдельный обычный bridge, не air gap; торрент-файлы, индексаторы и загрузки не добавляются. VueTorrent mod не устанавливается: проверяется backend API, не frontend или весь Compose.

На стенде выбраны одинаковые случайные номера внешнего порта и `WEBUI_PORT`, поскольку защищённый WebUI 5.2.4 отклоняет несовпадающий `Host` port. Это изменение параметра отдельного тестового контейнера; рабочий Compose с внутренним портом 9080 не меняется. Сценарий сам проверяет отрицательный запрос с несовпадающим портом. Если будущий мастер поддерживает другой внешний порт, его HTTP-путь требует отдельной проверки; автоматическое отключение Host validation не является решением.

Выполняются вход с временным паролем из памяти, настройка `/data/torrents` и incomplete, создание `movies`/`tv`, повтор без дублей и отказ при конфликте пути. Первый успешный ответ создания `movies` намеренно теряется в HTTP handler: следующий вызов наблюдает сервер и не повторяет POST. После смены credentials отдельные клиенты подтверждают отказ старых и вход новых; после остановки/старта проверяется сохранённое состояние до возможных записей. Passwords/cookies/полные preferences и Docker logs не выводятся и не сохраняются в отчёты. Сам qBittorrent пишет временный пароль в собственный стартовый журнал, который удаляется вместе с тестовым контейнером.

Запись не повторяется автоматически при потерянном ответе. Конфигурационные операции `QbittorrentContractClient` пока являются M0-контрактами: требуется владение ресурсами, подтверждённая сессия и закреплённая версия. При смене credentials клиент выводится из использования даже при ошибке/отмене; результат проверяется новым контекстом. Отмена во время записи также требует наблюдения состояния. Журнал установки и возобновление сценария мастера ещё не реализованы.

По завершении и при штатной отмене удаляются только ресурсы с проверенной меткой владения и без чужих mounts; cleanup имеет отдельные таймауты. Ошибка cleanup даёт ненулевой exit code и метку сессии для диагностики. При принудительном завершении процесса/потере Docker нельзя гарантировать удаление: перед ручной очисткой снова проверьте метку и mounts. Docker Desktop и скачанный образ остаются у разработчика.

## ArrDockerProbe: настройка и связи Arr

Нужны локальный Linux Docker Engine и четыре загруженных образа: qBittorrent `5.2.4_v2.0.15-ls479`, Radarr `6.4.4.10685-ls319`, Sonarr `4.0.20.3014-ls326`, Prowlarr `2.6.5.5623-ls163` из `lscr.io/linuxserver`. Инструмент сам не загружает образы. После сборки:

```text
dotnet run --project tools/HhHomelab.Wizard.ArrDockerProbe --no-build --configuration Release -- profiles/hh-homelab/1.3.0/research-profile.json
```

ArrDockerProbe требует точный источник v1.3.0 и четыре image pins. Создаёт четыре контейнера, отдельную обычную bridge-сеть, четыре config volumes и общий пустой data volume, без host bind mounts. Порты публикуются только на loopback; внутренние имена сервисов проверяются самими приложениями. Для qBittorrent Host/WebUI ports совпадают; динамические host ports Arr заново читаются после stop/start. Фиксированные папки создаются только в собственном data volume, без рекурсивного изменения прав медиатеки. Отказ от удалённого Docker и правила cleanup совпадают с QbDockerProbe. Общий developer harness находится в ProbeSupport; новых NuGet-зависимостей нет. Не собирайте проект поверх запущенного probe: Windows блокирует используемые DLL.

На каждом свежем стенде инструмент создаёт синтетический аккаунт qBittorrent и категории `movies`/`tv`, затем включает Forms/enabled у всех трёх Arr. Вход проверяется отдельным клиентом: UI недоступен до login, доступен после него; неверный пароль отклоняется. API требует ключ независимо от cookie веб-входа. Ключи читаются из config.xml только своих контейнеров и сохраняются в памяти.

Radarr и Sonarr получают `/data/media/movies` и `/data/media/tv`, download clients qBittorrent с соответствующими категориями; Prowlarr — два applications с `fullSync`. Каждый provider проходит API Test. Повтор читает ID и состояние, проверяет сохранённое подключение и предоставленные credentials, не выполняет create/update. Маскированные секреты нельзя сравнить с исходной строкой: Test доказывает работоспособность сохранённого доступа, а не равенство скрытых строк.

Первый успешный ответ создания root folder Radarr искусственно теряется: следующий вызов сначала наблюдает созданную папку. Проверяется конфликт host у download client. После stop/start всех контейнеров исходные ключи/credentials и настройки должны пройти проверки без конфигурационных записей. Индексаторы не добавляются; передача индексаторов, загрузки, импорт, hardlinks, Jellyfin и DSM ACL этой пробой не проверяются.

Контракты Arr — исследовательские операции для собственной новой конфигурации. Они отказываются от чужих папок/providers и политик аутентификации, проверяют закреплённую версию перед записью, не повторяют запросы автоматически и возвращают безопасный код/HTTP status. При потере ответа или отмене во время записи нужно наблюдать сервер; журнал установки, защита от конкурирующих запусков и resume engine появятся позже. Пользовательский мастер не должен применять эти методы без проверки владения и движка установки.

## MediaDockerProbe: Jellyfin и Seerr

Нужны локальный Docker с Linux Engine и поддержкой `volume-subpath` (Docker Engine 26+; локально проверен 29.8.2), SDK из global.json и четыре заранее загруженных образа:

```text
docker pull lscr.io/linuxserver/radarr:6.4.4.10685-ls319
docker pull lscr.io/linuxserver/sonarr:4.0.20.3014-ls326
docker pull lscr.io/linuxserver/jellyfin:12.2ubu2604-ls53
docker pull ghcr.io/seerr-team/seerr:v3.5.0
dotnet run --project tools/HhHomelab.Wizard.MediaDockerProbe --no-build --configuration Release -- profiles/hh-homelab/1.3.0/research-profile.json
```

MediaDockerProbe принимает только точный источник и четыре pins профиля v1.3.0. Runtime API подтверждает Jellyfin **12.2.0** и Seerr **3.5.0**; упаковочный tag Jellyfin не заменяет эту проверку. Стенд создаёт четыре контейнера, четыре config volumes, общий пустой data volume и отдельную обычную bridge-сеть; порты доступны только на loopback. Host bind mounts отсутствуют. Jellyfin получает только подкаталог `media` в `/data/media` read-only и временный `/cache`; torrent-папки ему не доступны. Это fixture mounts, не испытание Compose или ACL NAS. Правила владения, отказа от удалённого Docker и cleanup совпадают с ArrDockerProbe.

На свежем стенде настраиваются Forms/enabled и root folders двух Arr, первый администратор Jellyfin, локаль ru-RU/RU/ru, отключение внешнего доступа приложения и завершение startup. Создаются библиотеки «Фильмы» и «Сериалы», без запуска сканирования. Авторизация использует современный `Authorization: MediaBrowser … Token=…`; legacy-режим Jellyfin не включается. Повтор сначала пробует предоставленные credentials: после установки первого пароля анонимный Startup/User уже недоступен, даже при незавершённом wizard. Чужой пароль или конфликтующая библиотека не исправляются сбросом.

Seerr создаёт первого владельца через Jellyfin, затем новый cookie context подтверждает owner ID, Jellyfin user/server IDs, сохранённый адрес и работоспособность сохранённого доступа через список пользователей Jellyfin. Список библиотек синхронизируется при пустом состоянии; включаются только две библиотеки с подтверждёнными ID, именами и типами. Для обоих Arr probe явно выбирает существующий HD-1080p из live API Test и проверяет root folder. Это выбор синтетического сценария; продуктовая настройка профиля и поиска принадлежит пользователю. Сохранение связи само по себе не выполняет Seerr Test, поэтому клиент вызывает Test до/после создания и при повторе. Завершение setup требует ещё одной проверки библиотек, сохранённых связей и выбранных profiles/root folders.

Успешный ответ теряется в handler после пяти реальных записей: пароль администратора Jellyfin, библиотека, первый login Seerr, связь Radarr и initialize. Затем наблюдается состояние; повторный create не выполняется. Неверные пароли проверяются в новых контекстах Jellyfin/Seerr. При повторе и после stop/start всех четырёх контейнеров transport запрещает конфигурационные записи; разрешены GET, login и API Test. Login создаёт сессии, поэтому это не утверждение об отсутствии любых записей в БД. Проверяются прежние credentials, server/user/library IDs, enabled-флаги, Arr links и initialized.

CI `media-runtime` выполняет два свежих сценария; фактический результат публикуется в PR.

Секреты остаются в памяти, не входят в вывод и отчёт. Ничего не добавляется в индексаторы, загрузки или запросы Seerr. Обычный пользователь Jellyfin, его policies, сканирование, воспроизведение, транскодирование и проверка импорта/hardlinks не выполнены. Потеря HTTP-ответа после завершённой записи не моделирует падение сервера посреди первой авторизации Seerr: создание owner, ключа Jellyfin и сохранение настроек не атомарны. Восстановление такого частичного состояния требует отдельного контракта. Journal, идентичность ресурсов собственной установки и защита от параллельного применения остаются задачами движка; эти методы нельзя применять к произвольной существующей конфигурации.

## HaDockerProbe: Home Assistant

Нужны локальный Linux Docker Engine, SDK из global.json и заранее загруженные образы HA и Jellyfin профиля. Python на компьютере разработчика не нужен; используется штатный runtime образа HA.

```text
docker pull ghcr.io/home-assistant/home-assistant:2026.10.0
docker pull lscr.io/linuxserver/jellyfin:12.2ubu2604-ls53
dotnet run --project tools/HhHomelab.Wizard.HaDockerProbe --no-build --configuration Release -- profiles/hh-homelab/1.3.0/research-profile.json
```

Инструмент принимает только точные tag/commit источника и pins HA/Jellyfin профиля v1.3.0. Создаёт собственные сеть, два config volumes и три контейнера: одноразовый seed с публичной минимальной YAML-конфигурацией, штатный HA Container и Jellyfin peer. Нет host bind mounts, Docker socket, устройств и Supervisor; порты публикуются только на loopback. Seed не записывает пароли и не редактирует `.storage`. Jellyfin использует временный cache и пустую конфигурацию, без медиатеки. Основной HA сохраняет штатный `/init`, необходимый для restart. Удаление проверяет владение/mounts, использует отдельные таймауты и распространяет ошибку cleanup в exit code. После stop/start динамический host port заново читается.

Первый [config flow Jellyfin](../contracts/jellyfin-flow.md) подключает сервис по адресу внутри Docker-сети из самого HA. Проба получает отказ неверного пароля, явно передаёт исправленный и подтверждает loaded entry/server device, затем повторяет чтение после restart при запрещённых flow POST. Администратор Jellyfin синтетический; служебный пользователь, его policies и реальный media_player этим сценарием не проверяются. Состояния неизвестного исхода start/submit и отмены проверяются fixtures, а не инъекцией потери config-flow ответа в runtime.

WebSocket greeting подтверждает точную версию **до отправки credentials**. При незавершённом user step создаётся первый владелец, код обменивается через `/auth/token`, затем подтверждаются owner/admin/name и отсутствие safe mode. Потерянный ответ создания владельца восстанавливается обычным login flow; завершённый шаг не отправляется повторно. После полного onboarding и restart endpoint статуса может отсутствовать (404); владелец всё равно проверяется обычным login, 404 не считается доказательством credentials. MFA/неожиданный шаг login не обходится. Пароли, auth codes, access/refresh tokens остаются в памяти клиента, не экспортируются и не выводятся. Сервер сохраняет собственное состояние в disposable volume.

Для теста через HA API создаётся настоящий локальный `input_boolean`. Он не заменяет отсутствующие датчики DSM. Переименование сверяет registry ID, unique ID, platform, config entry, device, disabled state и коллизии назначения. Уже переименованная та же запись наблюдается без второй записи. Не выбирается первый sensor/player; общий apply/recovery ролей и циклические переименования пока не реализованы. Ограниченный enable выбранной registry identity описан ниже.

Создаётся отдельная storage-панель `hh-homelab-m0` с явным списком включённых зарегистрированных сущностей. Создание, сохранение и readback идут через Lovelace API, без редактирования `.storage`. Другая metadata/config блокирует перезапись. Это проверка API на простой entities card; полный YAML dashboard исходного проекта, рендер, визуальное отображение и разрешение всех ссылок не проверены.

HTTP protection требует состояния `RUNNING`, а не только доступного сокета. Включается IP ban с threshold=5, отключённым X-Forwarded-For и пустыми trusted proxies. Порт остаётся 8123; чужие порт/TLS/proxy-настройки блокируют этот ограниченный контракт. `configure` сохраняет pending и перезапускает HA. Затем клиент явно переподключается, обновляет access token из памяти, подтверждает прежнего владельца, RUNNING, active pending без error и наличие revert deadline; только после этого выполняет `promote` и readback stable. Сравнивается весь ожидаемый HTTP config без metadata сервера, включая сохраняемые поля CORS/host; failed/foreign/reverted trial не подтверждается. Автоматический rollback по истечении пяти минут известен из исходников, но ожидание таймера на живом стенде не проверено; такие состояния покрыты fixtures. Сам IP ban под нагрузкой/достижением лимита не испытывался.

Семь успешных ответов намеренно теряются после записи: owner, entity enable, registry rename, dashboard create, config save, HTTP configure и promote. Следующий вызов наблюдает сервер; транспорт не повторяет записи. Отмена не означает откат. При повторе и после restart транспорт блокирует конфигурационные изменения; разрешены read, login/token и check_config. Авторизация может писать сессии/токены на сервере, а check_config является проверочным POST. Поэтому это не утверждение о нуле любых серверных записей.

WS поддерживает текстовые фрагменты с лимитом 1 MiB, последовательные command IDs и пропуск event frames; подписки, binary/coalesced messages и универсальный публичный command API не предоставляются. `ha-runtime` повторяет пробу дважды в Ubuntu CI; фактический результат фиксируется в PR.

HomeAssistantContractClient требует `await using` / `DisposeAsync`: HTTP-клиент остаётся доступным до завершения асинхронного cleanup. Отзывается только полученный этим клиентом refresh token через `/auth/revoke`; пустой HTTP 200 является нормальным ответом. Новая авторизация сначала отзывает прежнюю сессию, reconnect использует существующий refresh token. Ошибка проверки owner/config после выдачи токена вызывает отдельный cleanup, даже если исходная операция отменена. `DisposeAsync` выполняет best effort и сохраняет `SessionCleanupFailure`, не подменяя исходную ошибку при выходе из `await using`. Когда подтверждённый отзыв обязателен для успеха, нужен явный `RevokeSessionAsync` и проверка `SessionRevocationConfirmed` до уничтожения HTTP transport. После неудачного dispose явный отзыв можно повторить на ещё живом HTTP-клиенте. Проба проверяет metadata собственных сессий через `auth/refresh_tokens`, не читает токены из `.storage` и не удаляет чужие сессии.

Совпадение pending HTTP config с желаемым недостаточно: клиент должен сам начать configure, затем переподключиться и проверить trial. Новый клиент отказывает и Stage, и Confirm для идентичного чужого pending. Без долговечного журнала M3 перенос намерения между процессами пока не поддерживается; такой trial не подтверждается автоматически. Потеря ответа собственных configure/promote на том же клиенте по-прежнему восстанавливается наблюдением. Внутренний deadline WS/HTTP классифицируется как неизвестный результат записи или ошибка чтения; `OperationCanceledException` сохраняется только при отмене вызывающего token. Отмена записи всё равно требует выяснить фактический результат.

Cleanup не решает случаи принудительного завершения процесса, недоступного HA или потери ответа выдачи токена, когда само значение refresh token не получено. Безопасное хранение и восстановление сессии относятся к M3; существующие чужие токены не удаляются ради очистки.

Минимальная fixture-конфигурация и простая панель отличаются от полного hh-homelab. Стандартный core onboarding HA может создавать предусмотренные самим HA интеграции и обращаться к интернету; обычная bridge-сеть не является air gap. Мастер не настраивает облачные аккаунты в этой пробе. Полное сопряжение Synology/LG/GX1, показания и управление устройствами не проверены. Доставка Monitor Docker, полный локальный профиль и ускоренные прикладные сценарии проверяются отдельными HaProfileProbe/HaRuntimeProbe, а `check_config` здесь подтверждает минимальный YAML стенда. Journal, маркер собственного HA и защита от конкурирующих запусков остаются задачами установщика; адаптер требует уже проверенного владения и сериализации операций.

## DesktopProbe

DesktopProbe — инструмент разработчика: открывает настоящее Win32/X11/Wayland окно, выполняет программные команды сценария на реальном composition root и сохраняет рендеры только собственного окна в `artifacts/native-desktop`. К NAS не обращается. `--expect-backend Win32|X11|Wayland` проверяет фактическую реализацию окна; fallback не может выдать успешный результат нативной Wayland-пробы. Headless тесты отдельно проверяют compiled bindings, мышиные клики, состояние команд, минимальную ширину, темы и масштаб 150%.

```text
dotnet run --project tools/HhHomelab.Wizard.DesktopProbe --no-build -c Release
```
